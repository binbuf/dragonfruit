# T188a — T-21.2b per-output presentation clock (pure)

## Landed

- New pure library module `compositor/src/presentation.rs`, exported as
  `dragonfruit_compositor::presentation` from `compositor/src/lib.rs`.
- `PresentationClock { last_presented, next_deadline, period, refresh_hz, vrr }`
  with `new(OutputRefresh)`, `with_period(Duration, VrrState)`,
  `set_refresh(OutputRefresh)`, `note_presented(timestamp)`, `is_idle()`,
  `is_due(now)`, and `time_until_due(now)`.
- `PresentationClocks`, a `BTreeMap` keyed by output name, with `update`,
  `remove`, `clear`, `get`, `get_mut`, `note_presented`, `iter`, `len`,
  `is_empty`.
- `DfState` owns `presentation_clocks`; output add/mode change/resume update
  the clock from the same effective refresh (`refresh_for_output`, so the
  diagnostic override applies), and output removal drops it. A presentation
  that races removal is ignored rather than resurrecting the clock.
- DRM `frame_finish()` calls `state.note_presentation()` with the kernel
  monotonic vblank timestamp (or the compositor-clock fallback) only when
  `frame_submitted()` confirms a queued frame.
- Nested damage path calls `state.note_presentation()` with `state.clock.now()`
  immediately after a successful `submit()`. No-damage swaps are not clock
  samples.
- ADR `docs/design/adr/0200-per-output-presentation-clock.md`,
  `docs/design/02-compositor.md`, `docs/rendering.md` R3.2, and
  `docs/design/STATUS.md` G-02 updated. No scheduling, timer, or render-gate
  changes.

## Semantics / reusable facts

- Timestamps are monotonic `Duration`s, not `Instant`s, so the module is pure
  and unit-testable.
- `note_presented(t)` sets `last_presented = t` and
  `next_deadline = t + period`. A missed deadline stays due and the next
  presentation re-anchors; it never queues catch-up frames.
- A never-presented clock has `last_presented = None`,
  `next_deadline = None`, and `is_due()` returns true (first frame due).
  `time_until_due()` returns zero. This is a timing predicate, not a render
  request: T188b must gate it on the per-output request set so an idle output
  is not woken by another output's animation.
- A stale timestamp older than `last_presented` is ignored (`note_presented`
  returns false).
- `with_period(Duration::ZERO, vrr)` falls back to 60 Hz; out-of-range periods
  clamp to 24–500 Hz, matching the refresh model. Do not construct a
  zero-period clock by hand.
- 60 Hz period = 16,666,666 ns; 144 Hz = 6,944,444 ns; 143.999 Hz =
  6,944,492 ns.
- `refresh_hz` is the resolved `OutputRefresh::refresh_hz()` (millihertz /
  1000), so a 143.999 Hz mode stays 143.999 rather than 144.
- Nested `submit()` returns only `Result<(), SwapBuffersError>`; Smithay's
  winit backend exposes no platform vblank timestamp. The completion time is
  `state.clock.now()` right after the swap returns. This is a single-output
  correctness rail, not mixed-refresh evidence.

## Follow-ups

- T188b: replace the global `needs_redraw` animation gate with per-output
  requests; use `PresentationClocks` + `is_due`/`time_until_due`, gated by
  the request set, and arm one timer from the earliest due deadline. Update
  the clock after each presented frame; do not re-arm a settled output.
- T188b: move the missed-deadline rule (1.5× period) onto the presentation
  clock/summary and include `refresh_hz` per output.
- T188c: VRR adaptation and mixed 60+144 evidence; the clock carries `vrr`
  but never infers it from one interval. Nested is not mixed-refresh proof.
- T188b/c: chrome frame callbacks on every presented output frame and the
  no-damage callback path.
