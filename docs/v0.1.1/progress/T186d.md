# T186d — T-21.1d GPU transport: rollout, stats, and docs

## Landed

- `ShellController::commitChromeScene()` is the single commit path for every
  chrome scene. Targets carry the stable stats label, logical size, source
  rect, shm fallback lambda, and (for lock) the opaque lock surface id.
- `ShellProtocol::commitDmabufFor(label, ...)` and `commitLockDmabuf(id, ...)`
  wrap `commitDmabufTo()`; every mapped surface now uses them.
- Shared scenes (menubar + menubar-popup, dock + dock-popup) export once and
  commit the same frame to both surfaces. `ChromeDmabufReleaseTracker` keeps
  the producer slot busy until the last `wl_buffer.release`.
- No readback after a dmabuf commit. If no target commits, the frame is
  abandoned and read back once for shm; if some targets commit, failed targets
  are retried/disabled and the whole scene moves to shm on the next frame.
- Per-surface `chrome surface` stats gained `path=dmabuf|shm` and
  `gpu_reason=`; the existing buffer/copy/commit counters remain.
- `DRAGONFRUIT_CHROME_GPU_SURFACES` (comma-separated labels) is a capture-only
  filter; empty means all surfaces.
- ADR 0197, `docs/rendering.md` R2.3, `docs/design/04-shell.md`,
  `docs/captures/README.md`, and the task Hand-off are updated.
- Captures: `docs/captures/t21-gpu-rollout.txt` and
  `t21-gpu-rollout-{dock,menubar,popover,lock,fallback}.png`;
  `scripts/t21-gpu-rollout.sh` + `make t21-gpu-rollout`.

## Reusable facts / gotchas

- `commitChromeScene()` records `recordRender()` only on the GPU path; the shm
  path records through `renderChromeFrame()` using the window object name.
  Keep those labels aligned with `surfaceLabel()`.
- A shared scene is all-or-nothing: if any target is in
  `m_chromeDmabufDisabled` or excluded by `DRAGONFRUIT_CHROME_GPU_SURFACES`,
  the whole scene uses shm. This avoids reading back an FBO the compositor is
  already sampling.
- Never call `readbackCurrentFrame()` after a successful dmabuf commit; the
  FBO may still be referenced by the compositor and the readback can block on
  the GPU fence.
- `deferChromeProducer()` uses the 100 ms fallback timer for transient export
  failures instead of spinning an immediate render. `wl_buffer.release`
  schedules the retry directly.
- The popup surfaces use the owner producer's ring (`chromePaceLabel()` maps
  `menubar-popup` -> `menubar`, `dock-popup` -> `dock`). Do not treat them as
  independent producers.
- `DRAGONFRUIT_CHROME_GPU_SURFACES` is capture-only. It does not change the
  default and must not be presented as a user setting.
- The T186c report `t21-dmabuf-ring.txt` is owned by T186c; do not commit a
  T186d rerun over it unless the T186c assertions are updated.
- KWin virtual and the real host session both show implicit-sync stalls under
  repeated multi-surface dmabuf animation. A clean capture usually comes from
  one scenario per fresh compositor, no fast sweep, and stats before the
  screenshot fixture fires.
- Screenshot fixture output can land in `~/Pictures/Screenshots` instead of the
  requested temporary path; accept the newest screenshot as a fallback.

## Follow-ups

- T192/T193: default-on, benchmark/soak, and explicit `linux-drm-syncobj-v1`
  acceptance. The implicit-sync shared-scene stall is the main blocker.
- Consider a larger per-producer ring (or a deferred ring-exhaustion policy)
  for two-surface scenes; the current three-slot ring can exhaust before the
  compositor releases the previous frame.
- Consider committing one shared `wl_buffer` to both surfaces of a shared
  scene instead of importing the same fd twice; this may reduce the implicit
  sync stall observed when the popup first opens.
- Native DRM acceptance and multi-GPU/rotated output remain out of scope.
