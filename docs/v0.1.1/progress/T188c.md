# T188c — T-21.2b VRR, chrome callbacks, and mixed-refresh evidence

## Landed

- `PresentationClock` (T188a) now owns a backend-supplied `VrrRange` plus the
  last measured interval. A clock adapts only when `VrrState::On` *and* a range
  is installed; an in-range presentation interval becomes the next deadline,
  an out-of-range one falls back to the nominal mode period. One interval never
  turns VRR on. `presentations` and `last_interval_us` are exposed for
  per-output cadence evidence.
- `DfState` owns `output_vrr`. `refresh_for_output`, `on_output_mode_changed`,
  `recompute_refresh_schedule`, and output removal all carry it; `set_output_vrr`
  reinstalls the clock range. DRM probes `DrmCompositor::vrr_supported` /
  `vrr_enabled` at connector connect: `Supported` is enabled without a modeset,
  `RequiresModeset`/`NotSupported` keep the fixed period (`off`/`unsupported`).
  Nested/headless stay `Unknown` and report `vrr=unsupported`. `df_output.vrr`
  reports the real `On` state instead of a hardcoded zero.
- `presentation stats` and `frame request` append `vrr`, the accepted interval,
  the range, `presentations`, and `last_interval_us`.
- Chrome frame callbacks were already sent from `post_repaint` (presented
  frame) and `send_frame_callbacks` (no-damage path); the new trace proves the
  counter advances with the shell's `wl_surface.frame` requests. No render-path
  change was needed.
- Mixed-refresh hook: `frame_scheduler::tests::mixed_refresh_60_and_144_with_one_idle_and_one_animating`
  runs 60 Hz + 144 Hz with a third idle output and asserts the fast output keeps
  ~144 presentations/s, the slow output ~60, and the idle output 0.
- Synthetic-output harness: `add <name> <w> <h> <x> <y> [scale] [refresh_mhz]`
  (default 60000 mHz). Synthetic-input harness: `animate-dummy-on <output>
  <ms>` scopes the calibration animation to one output.
- Capture: `scripts/t21-vrr-mixed-refresh.sh` / `make t21-vrr-mixed-refresh`
  writes `docs/captures/t21-vrr-mixed-refresh.txt` and the native
  `docs/captures/t21-vrr-mixed-refresh-native.txt` OPEN marker.
- Docs: ADR `0202-vrr-adaptation-and-mixed-refresh-evidence.md`,
  `02-compositor.md`, `rendering.md` P4/R3.3, `STATUS.md` G-02/G-13,
  `docs/captures/README.md`.

## Reusable facts / gotchas

- VRR is never inferred from a measured interval. `VrrState::Unknown` is the
  `vrr=unsupported` token; `Off` is a fixed-refresh backend that exposes the
  capability but is not enabled.
- `VrrRange::for_mode_period(period)` is mode period → 24 Hz. `set_refresh`
  clears the range/interval; `DfState::apply_clock_vrr` must reinstall it after
  every `presentation_clocks.update`.
- The missed-deadline rule still uses the nominal deadline, so a 60 Hz animation
  on a 144 Hz output is counted as missed even when VRR is active. That is the
  intended health rule, not a VRR scheduling bug.
- `animate-dummy` (unscoped) requests every output. `animate-dummy-on` sets
  `DfState::dummy_animation_output`; `animation_output_names` returns only that
  output while the animation is live. Test plumbing only.
- The nested host throttles `submit()` to roughly 1 Hz. Nested `last_interval_us`
  is therefore ~1 s; use the derived 144 Hz period and the request lifecycle as
  the single-output evidence, not the measured nested interval.
- `scripts/t21-vrr-mixed-refresh.sh` polls `frame scheduler stats` until
  `animation=0 timer_armed=0` before taking a settled sample; the nested rail
  needs this because a fixed sleep is not enough.
- Native mixed-refresh is OPEN on this host: only `card1-DP-1` is connected and
  the live native session cannot be restarted. The OPEN artifact records the
  exact rerun command.
