## Goal

Empty Trash becomes an asynchronous operation with visible states: a delayed
busy indicator while it runs, then a success result (check + removed count) or a
failure (message + **Try Again**), instead of a silent synchronous call behind a
confirmation.

## Context (read first)

- `shell/src/trashbridge.{h,cpp}` — the Dock's Trash state. `empty()` calls
  `df_files_trash_monitor_empty` synchronously and returns an item count; a
  worker thread already exists for the change watch.
- `services/files-core/src/ffi.rs` — `df_files_begin_empty_trash` (returns an
  `OpId`), `df_files_pending_ops`, and `df_files_take_error` exist for the
  session/op path; `df_files_trash_monitor_empty` is the simple synchronous path
  the bridge uses today.
- `shell/dock/Dock.qml` `trashMenuModel` — the confirmation step
  (`trashConfirming`) that swaps the menu to `Empty Trash` / `Cancel`.
- `shell/src/shellcontroller.cpp` — the action handler
  (`empty_trash` / `empty_trash_confirmation`) and how the bridge result is
  applied.
- Legacy [10-dock.md](../tasks/legacy/10-dock.md) §16 promises "progress for
  large trash"; it is not implemented.
- Reference behavior only (GPL, never copied):
  `ConfirmTrashEmptyPopup.qml` / `TrashIntegration` in
  `~/repos/punchi-dock-remastered` show idle → emptying (busy after a delay, or
  a determinate bar with "N of M items") → succeeded (check + message) /
  failed (message + Try Again), with focus moved to the safe action.

## Current behavior (investigated, T110 era)

- Selecting Empty Trash confirms, then calls the synchronous files-core empty;
  the Dock shows no busy or result state and a failure is only a notice. Large
  trash blocks the UI thread for the duration.

## Scope

- [x] Make the empty asynchronous: run it on the bridge's existing worker (or
      use the files-core session/op path) and report `emptying` / `succeeded`
      (removed count) / `failed` (message) on the UI thread; never block the
      shell.
- [x] `Dock.qml`: extend the Trash menu/confirmation with the states — a busy
      indicator shown only after a short delay (so a fast empty does not
      flicker), a success state (check + removed count), and a failure state
      (message + Try Again). The confirmation stays the entry point.
- [x] No new persistent state and no polling: the bridge's existing event-driven
      watch updates the icon/badge; the operation result is a one-shot signal.
- [x] Accessibility: state changes are announced (busy/result/retry); focus
      moves to the safe action.
- [x] Reduced motion: state changes are instant; the busy indicator still
      distinguishes "working" from "done".
- [x] Tests: `tst_dock.qml` for the state progression and Try Again;
      `tst_dockcore` for the bridge/worker result mapping; a files-core absence
      case (service down → failure, never a hang).
- [x] Capture `docs/captures/t14-dock-trash-empty.png` (busy + success) and the
      `PROGRESS.md` note.

## Explicitly deferred

- Determinate `N of M` progress: files-core exposes no item-count progress for
  the empty operation; add it behind a progress seam first (a files-core unit),
  then surface it here. Record the seam in the Hand-off.
- Trash sounds and desktop notifications (KDE-reference behavior; not our
  design).
- Empty-on-drop and other Trash mutations beyond Empty Trash.

## Design notes

- One operation at a time per Trash entry; a second Empty Trash while
  `emptying` is ignored.
- The bridge stays the owner of Trash state; the Dock renders. Do not add a
  second Trash reader (ADR 0052).
- A failed empty must leave the Trash state intact (the monitor re-reports the
  real count) and offer Try Again without re-opening the menu.

## Hand-off

**Async seam chosen.** `TrashBridge` (shell/src/trashbridge.{h,cpp}) gained an
`EmptyState` machine and `emptyAsync()`: it starts a one-shot `std::thread`
(separate from the watch worker, which stays blocked on
`df_files_trash_monitor_wait`), and posts `emptyFinished(ok, removed, error)`
back to the UI thread with `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`.
The synchronous `empty()` remains for the drop path/tests. The files-core
session/op path (`df_files_begin_empty_trash`) was **not** used: it drives a
Files listing, not the Dock's count-only monitor, and would need a session per
empty. `FfiTrashMonitor` is internally synchronized, so the worker may call
`empty` while the watch worker waits.

**States.** idle → emptying (a delayed indeterminate ring after
`component.dock.trashEmpty.busyDelay`, default 350 ms) → succeeded (check +
"`N` items removed") / failed (message + **Try Again**). The confirmation step
in `trashMenuModel` stays the entry point; confirming calls `beginTrashEmpty()`
in Dock.qml, which closes the menu and opens `DockTrashEmptyPopover.qml`
anchored to the Trash entry. One operation at a time is enforced in the bridge
(`emptyAsync` returns false while `Emptying`); `retryTrashEmpty` emits
`empty_trash` again without re-opening the menu. Focus moves to Try Again on
failure; `Accessible.announce` fires on every phase change. Reduced motion
stops the ring's rotation but the ring/gap still reads as "working".

**Progress seam files-core would need for N of M.** The empty operation
(`FreedesktopTrash::empty` → `df_files_trash_monitor_empty`) returns only the
final removed count. A determinate bar needs an item-count stream — e.g. a
`df_files_trash_monitor_empty_with_progress(monitor, cb, user)` that walks
`files/`+`info/`, invokes `cb(removed, total)` per item, and still returns the
final count — or an op handle polled like `df_files_pending_ops`. No such seam
is added here; the indeterminate ring is the fallback.

**Failed empty leaves state intact.** A failure does not mutate the store; the
monitor's event-driven watch re-reports the real count, so the badge stays
honest. The result is a one-shot signal (`handleTrashEmptyResult`); a result
arriving after the popover is dismissed is dropped.

the live check still ran the nested session. `make check` stops at the

(unchanged); every other gate is green. An ADR (0106) records the seam.

**Next task must know.** T-14.7s should not re-derive Trash state: the bridge
owns it (ADR 0052). The result path is `onTrashEmptyFinished` →
`handleTrashEmptyResult`; a new state must be added to `DockTrashEmptyPopover`
and the bridge's `EmptyState`, not to the context menu. Determinate progress is
blocked on a files-core seam (above).
