# T201 — Menu-bar visibility settings

## What landed

- **`menu.showBackground` is one switch for both rails.** The QML fill and the
  compositor panel/veil already shared `compositorPanelActive`; T201 covers the
  toggle in `tst_menubar` for the replacement veil and the legacy sampled rail,
  and the compositor clears the explicit region set when it is off. Items, hit
  targets, keyboard entry, and the 28 pt reservation stay intact.
- **`menu.autoHide` is compositor-owned per output.** Additive
  `df_layer_surface.set_auto_hide` (protocol v4) carries
  `never`/`always`/`full_screen`. `compositor/src/shell/menubar.rs` owns
  `AutoHideMode`, the pure `menu_bar_visible` rule, and `MenuBarVisibility`
  (mode + per-output reveal). The shell forwards the setting from
  `applyMenuBarPolicy` on the existing `changed`/`refreshed` path.
- **Reveal paths.** Pointer motion in the top `menuBar.height` band reveals
  before hit-testing; Control-F2 (`InputAction::FocusMenuBar`) reveals and
  focuses the bar. An open menu/focus (`menu_bar_active_on`, cached in
  `focus_changed` to avoid the Smithay keyboard mutex) keeps it up. Moving
  below the band conceals unless active; release/lock clears the reveal.
- **Reservation and scanout.** A concealed bar is filtered out of
  `visible_chrome_surfaces`, so it contributes no reserved zone, input hit
  area, material region, veil, or blur panel. `refresh_reserved_zones` filters
  the menubar per output. A visible `never` bar over fullscreen is a real
  composition requirement and keeps the material pass (no direct scanout).
- **Startup is hidden for `always`.** The initial seat position (0,0) does not
  count as an edge reveal (`menu_bar_pointer_seen`); the first real motion or
  keyboard focus reveals.
- **Diagnostics.** `query menubar` prints the mode and per-output
  `fullscreen/revealed/active/visible/reserved-top` state.
- **Docs.** `docs/settings-keys.md` + `services/settingsd/src/schema.rs`
  consumer strings, `docs/design/02-compositor.md`, `04-shell.md`,
  `07-system-integration.md`, `docs/private-protocols.md`, ADR 0210 note, and
  new ADR 0220.

## Reusable facts / gotchas

- The menu bar is **one all-output layer surface**. Per-output reveal is a
  filter in `visible_chrome_surfaces`/`refresh_reserved_zones`, not a second
  surface.
- Do not query `keyboard.current_focus()` from `focus_changed`: Smithay holds
  the keyboard mutex. Use the cached `DfState::menu_bar_keyboard_focused`.
- Smithay's `set_focus(None)` sends the leave but does **not** invoke
  `focus_changed`; every unset path must clear the cache and call
  `sync_menu_bar_reveal()`.
- `set_auto_hide` is not commit-latched (unlike panel regions); send it and
  flush. The shell stores the latest value and sends it in
  `createMenuBarSurface` if settings applied before the surface existed.
- `query menubar` is the fast headless proof; `query scale` also hides a
  concealed menubar because it uses `visible_chrome_surfaces`.
- The reveal is an immediate flip (no unmeasured animation curve), so
  reduced-motion is honored trivially.

## Follow-ups

- T202: menu-family glass must stay below the veil and follow the same
  visibility filtering.
- T208: native DRM evidence for a `never` bar over fullscreen (visible, no
  scanout) and a concealed bar (scanout candidate) belongs to the native rail.
- A measured reveal animation can be added later behind the shared motion
  policy; the current state flip is the documented baseline.
- The QML `visibleIn()` rule is a scene/test copy; if a future shell needs to
  animate reveal, the compositor should send a visibility event rather than
  re-deriving the policy in QML.
