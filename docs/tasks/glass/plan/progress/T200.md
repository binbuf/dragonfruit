# T200 — Menu-bar no-blur veil

## What landed

- **Measured Light depth LUT.** `design-system/tokens/tokens.json` now stores
  the eight reference samples under
  `glass.presets.menuBarVeil.{light,dark}.veil` plus `stripHeight: 39` and
  `extent: 95`. Light `neutralTint` is 1.0 (a white lift); Dark is 0.0 (a black
  wash) with the same depth shape scaled to a 0.48 peak. Generated consumers
  are `compositor/src/design_tokens.rs` and `design-system/Theme.qml`.
- **Pure veil model.** New `compositor/src/window/menubar_veil.rs` owns
  `VeilSpec`, the piecewise-linear `alpha_at` LUT (exactly zero from 95 pt),
  the bounded readability correction (`adapted_alpha`), checker transmission,
  shader uniforms, and the `material veil` diagnostic. `VEIL_FILTER` is
  `RegionFilter::Sharp`.
- **Veil shader.** `compositor/src/window/blur.rs::VEIL_SHADER` samples the
  sharp scene at the current pixel, reconstructs the output-relative depth from
  `panel_uv_offset/scale`, and uses a 5-tap luminance probe only to choose a
  higher alpha inside the 39 pt strip. It never filters the displayed colour.
  `BackdropBlurElement::with_veil` carries it; `nested` and DRM compile it once
  and attach it on the sharp path. A refused shader falls back to the flat-band
  glass plate.
- **Compositor resolution.** `BlurPanel` gained `veil: Option<VeilSpec>`;
  `chrome_blur_panels` builds it only for `RenderMode::NoBlurVeil`. The sharp
  element commit now follows the scene cache's real-damage commit
  (`PanelTextureSlot::note_sharp_scene_commit`), so a moving window under the
  bar repaints the veil while a settled scene does not. No Kawase allocation
  or blur counter is involved.
- **Shell/geometry split.** The menu-bar layer surface is configured to the
  95 pt visual extent, but the exclusive zone and committed buffer/input strip
  stay the 28 pt bar. The shell declares a `veil` panel region with the full
  extent and clears it when the QML resolution is not a compositor material.
  `MenuBar.qml` exposes `veilActive`, `compositorPanelActive`,
  `compositorPanelHeight`, `compositorPanelRadius`, `veilExtent` and
  `referenceStripHeight`.
- **No QML wash on the replacement rail.** In `no-blur-veil` mode the bar's
  QML colour is transparent; the compositor veil sits below the foreground and
  popups. Legacy rollout keeps the old sampled QML fill, and Reduce
  Transparency/no-sampling keeps the scheme-appropriate milky fallback.
- **Diagnostic + fixture.** `query material` prints
  `material veil mode=… extent=… strip=… probe=… tint=… readability=…
  alphas=…`. `scripts/t200-menubar-veil.py --check` is part of
  `make gates` via `make menubar-veil-check`; the evidence report is
  `docs/captures/t200-menubar-veil-model.json`.
- **Live nested capture.** `scripts/capture-t200-menubar-veil.sh` (make
  `menubar-veil-capture`) puts a black and a white X11 window directly under
  the bar and captures the compositor's own render for Light, Dark and the
  no-sampling fallback. Artifacts are
  `docs/captures/t200-menubar-veil-{light,dark,fallback}.png`, the matching
  `query scale`/`query material` text dumps, and the scored
  `docs/captures/t200-menubar-veil.md`/`.json`.
- **Tests.** `menubar_veil` unit tests (LUT tolerance/zero at 95, monotonic
  Dark shape, checker-size independence, live-window contrast, measured
  samples unchanged by adaptation, no-blur path), sharp-veil damage-commit
  test, layer extent/reservation/output-clipping test, protocol conformance
  test for commit-latched `veil` region + explicit clear, and QML tests for
  replacement/legacy/fallback/Reduce Transparency.

## Reusable facts / gotchas

- The veil is a **white lift in Light**, not a black alpha wash. Over black the
  measured output alpha is the white-overlay alpha; over white it is invisible.
- Sample depths are fixed at 5/15/25/35/50/75/90/95 pt. Alpha at/under 5 pt is
  the first sample; alpha at/over 95 pt is zero.
- The layer surface may be taller than its committed buffer. The shell
  configures 95 pt but commits the 28 pt strip; the compositor's `ChromeSurface.geometry`
  is 95, the input hit test is the buffer's 28 pt, and `reserved_rect` uses the
  exclusive zone 28. Do not commit a 95 pt buffer to the menubar surface or
  the veil region will duplicate the QML popup area.
- The shell reads `MenuBar.veilExtent` from QML after creating the item; keep
  the token binding alive.
- Menu-bar region requests set `m_menuBarPanelDirty`. The shm/dmabuf commit
  paths clear it, and the damage-free commit path calls
  `applyMenuBarSurfaceGeometry()` so a show/hide/material toggle still commits
  its metadata when the QML pixels did not change. Keep that path when T201
  adds auto-hide.
- `PanelKey` for the menubar is now `for_region(..., "veil")`, not the legacy
  `panel` key. The first frame after a shell upgrade rebuilds once.
- `query material` is the quickest headless proof:
  `XDG_RUNTIME_DIR=… DRAGONFRUIT_SYNTHETIC_INPUT=… DRAGONFRUIT_GLASS_ROLLOUT=replacement
  target/debug/dragonfruit-compositor --backend headless --socket-name …`, then
  send `query material` to the synthetic datagram path.
- `cargo test --bin dragonfruit-compositor` is where the `window` unit tests
  run; `--lib` does not include `window` (it is a binary-only module).
- `cargo clippy --all-targets -D warnings` still trips pre-existing
  `excessive_precision` in generated motion curves and `too_many_arguments`
  on the blur helpers; the gate does not run clippy.

## Follow-ups

- T201: wire `menu.showBackground` and `menu.autoHide` through
  `compositorPanelActive`; the hidden/revealed transition must keep the
  reservation/input contract and settle to zero veil work.
- T202: menu-family glass is separate; the veil must stay below those popups.
- Native DRM capture of the veil is still T208's rail; the nested Light/Dark/
  fallback captures are committed and the model/fixture covers the rest.
- Dark is a documented baseline, not a measured macOS profile. A controlled
  Dark capture can retune `dark.veil` without changing the model.
- The readability correction fades over 8 pt past the 39 pt strip to avoid a
  hard seam; keep that fade when retuning the Dark target.
- If both the veil and glass shaders are refused by a driver, the sharp path
  currently falls back to the raw scene; a solid-element fallback would be a
  safer last resort.
