## Goal

Every chrome surface that re-injects the compositor's pointer events into an
offscreen QML window goes through one timestamped helper, so the zero-timestamp
`DragHandler` grab that silently killed Dock clicks (T-14.7x) cannot recur on
the menu bar, Control Center, overview, popovers, screenshot/screencast, polkit,
or the notification banner.

## Context (read first)

- **The failure mode** (`docs/PROGRESS.md` T110x): the shell runs its chrome on
  the offscreen QPA and re-injects pointer events as hand-built
  `QMouseEvent`s. A `timestamp() == 0` event makes `QQuickDragHandler` measure
  a bogus movement on the press and take the grab, so a sibling `TapHandler`
  never taps. QtTest stamps its own events, so tests passed while the live
  session was dead.
- `shell/src/dockpointer.{h,cpp}` (new in T-14.7x, dockcore) —
  `DockPointer::timestamp()` (shared `QElapsedTimer`, `+1`) and
  `DockPointer::send(window, type, pos, button, buttons)`. The Dock path uses
  it; `shell/tests/tst_dock.cpp`'s `DockInject` context property wraps the same
  helper.
- **The unchanged injection sites** (`QMouseEvent` constructions in
  `shell/src/shellcontroller.cpp`): menu bar / main (`~3658`, `~3674`, `~3686`),
  Control Center (`~1979`, `~1997`, `~2007`), FileChooser (`~2371`, `~2388`,
  `~2398`), screenshot (`~2652`, `~2670`, `~2680`), screencast (`~2910`,
  `~2928`, `~2938`), polkit (`~3137`, `~3154`, `~3164`), overview (`~5157`,
  `~5177`, `~5187`), notification banner (`~5432`, `~5449`, `~5459`).
- T110x hand-off: *"The other chrome input paths … still build bare
  `QMouseEvent`s; they have no DragHandler siblings yet, so they are unchanged,
  but a new DragHandler there would need the same fix."*
- ADR [0110](../design/adr/0110-dock-pointer-injection-timestamps.md) records
  the rule; this unit makes it the chrome-wide rule instead of a Dock one.

## Current behavior (after T110x)

- The Dock is fixed; every other injection path still constructs bare
  `QMouseEvent`s with implicit `timestamp() == 0`. No user-visible bug today
  (none of those surfaces pairs a `TapHandler` with a `DragHandler` yet), but
  the next such pairing would ship dead controls with green tests.

## Scope

- [ ] Generalize the helper: reuse `DockPointer` (or rename it to a
      chrome-pointer helper — keep the API and a thin compatibility alias if
      renamed) as the single constructor for every injected pointer event;
      the timestamp is owned by the helper, never by the call site.
- [ ] Route every injection site listed above through it (move, button,
      leave), including the button-state bookkeeping each surface already
      keeps; no bare `QMouseEvent(...)` remains in those handlers.
- [ ] Tests: a unit test over the helper asserting nonzero, monotonically
      increasing timestamps across a sequence (including the first event); and
      one end-to-end injection case proving a stationary tap beside a
      `DragHandler` still taps through the shared helper (the Dock's
      `DockInject` case already covers the pattern — extend it or add a sibling
      for a non-Dock surface such as the menu bar).
- [ ] Keep the Dock behavior and `tst_dock`'s `DockInject` working unchanged
      (same helper, same button bookkeeping), and keep the offscreen-window
      injection seam documented.
- [ ] Docs: ADR 0110 gains the "all chrome injections" scope note;
      `docs/PROGRESS.md` gets the T151a note; the T110x gotcha is marked
      resolved across the chrome (not just the Dock).
- [ ] `ctest --test-dir build -R "tst_dock|tst_dockcore|tst_menubar|tst_controlcenter|tst_overview"`,
      `make qml-test`, `make e2e`, `make check` unchanged (run the subset the
      touched surfaces actually have).

## Explicitly deferred

- Replacing synthetic `sendEvent` injection with real QPA input
  (`QWindowSystemInterface`) — a larger input-plumbing change, out of scope.
- Touch/pen/stylus event synthesis.
- Per-surface pointer-device modelling (pressure, tilt) — not needed for taps.

## Design notes

- One constructor, one timestamp source: a call site that builds its own event
  is the bug. Make that mechanically obvious (a `ChromePointer`/`DockPointer`
  call), so a reviewer can grep for `QMouseEvent(` and find none.
- The helper must stay usable from tests (the context property in
  `tst_dock.cpp` is the precedent).
- No behavior change is intended: same positions, buttons, modifiers — only
  the timestamp differs. Any visible change is a regression.
