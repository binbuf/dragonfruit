## Goal

A stationary left click on **any** app/temporary/overflow entry activates or
launches it in a real session. Today the whole app region is dead to clicks
because a stationary tap never reaches the entry's `TapHandler` when the same
entry also enables a `DragHandler`; only Trash (and minimized/stack entries)
tap. The `DF_DOCK_ACTIVATION_FIXTURE` capture seam hides this and must be
retired.

## Context (read first)

- **The recorded root cause** — `docs/PROGRESS.md` "T110g" gotchas:
  *"Synthetic-tap limitation. In the shell's synthetic-injection path a
  stationary pointer tap does not land on a Dock entry that also enables a
  `DragHandler` (app/temporary); Trash/minimized/stack tap fine. The live
  capture therefore uses `DF_DOCK_ACTIVATION_FIXTURE`, which calls the real
  `onDockEntryActivated` path. Follow-up: fix the synthetic tap path and
  re-capture without the seam."*
- `shell/dock/DockEntry.qml` — the left `TapHandler` (`~540-554`) with
  `gesturePolicy: TapHandler.DragThreshold` / `dragThreshold: root.dragSlop`
  (8), the right-button `TapHandler` (`~572-580`), the stack `TapHandler`
  (`~562-570`), and the `DragHandler` (`~589-614`) enabled for app/temporary
  entries with the same threshold. A `HoverHandler` sits above them.
- `shell/src/shellcontroller.cpp` — `onDockPointerMoved`
  (`~5067-5079`), `onDockPointerButton` (`~5081-5099`), and
  `onDockPointerLeft` (`~5101-5109`) inject `QMouseEvent`s into `m_dockWindow`
  with the scene offset. The compositor delivers Dock-surface pointer events
  over the private shell protocol (the shell uses the offscreen QPA, so all
  Dock input is injected this way).
- `shell/dock/Dock.qml` — `handleEntryTap` / `activateEntry`
  (`~1214-1286`) and the `entryActivated` signal to
  `ShellController::onDockEntryActivated` (`~4744`), which is the one
  activation entry point (`activateAppOrFallback`, T-14.7g). T-14.7p's
  hover-open chooser must not swallow the click.
- `compositor/tests/shell_protocol_conformance.rs` —
  `dock_click_tree_activation_conformance` proves the protocol path, not the
  QML handler arbitration.
- `scripts/capture-dock-activation.sh` + `make dock-activation-capture` — the
  fixture seam and the captures that must be redone through the real pointer.

## Current behavior (reproduced, T110v era)

- `make demo`, real mouse: hovering magnifies, but a stationary click on a
  pinned app / temporary entry / overflow cell does nothing. In the same
  session the Trash (opens Files), a folder stack, and minimized entries
  respond, because their delegates do not enable a `DragHandler`.

## Scope

- [ ] Add a failing regression first: a `tst_dock.qml` case that injects a
      stationary press/release over an app entry whose `DragHandler` is
      enabled and asserts `activated` fires; plus (where feasible) a
      shell-level case that drives the real `onDockPointerButton` sequence
      into the offscreen window. The test must fail before the fix.
- [ ] Diagnose and fix the arbitration. Candidate fixes, in preference order:
      1. QML handler composition — give the left `TapHandler` the press and
         make the `DragHandler` take over only once the 8 px threshold is
         exceeded (`grabPermissions` / `PointerHandler.CanTakeOverFromHandlersOfDifferentType`
         / an explicit `onGrabChanged` handoff), so a stationary tap is never
         swallowed; or use a `MouseArea` for activation alongside the
         `DragHandler`;
      2. the injection itself — if the synthetic `QMouseEvent` sequence cannot
         complete a handler gesture (missing timestamps/device/points), send a
         proper pointer sequence (e.g. `QWindowSystemInterface::handleMouseEvent`
         or a fully-formed `QPointerEvent`) instead of bare `sendEvent`.
      The fix must preserve: drag reorder, hover magnification, the unified
      8 px tap/drag slop (ADR 0101), the hover-open chooser suppression
      (T-14.7p), and the right-button menu.
- [ ] Cover the other kinds (stack, Trash, minimized, overflow, folder/divider
      hit targets) so no delegate regresses; keyboard activation stays as is.
- [ ] Retire `DF_DOCK_ACTIVATION_FIXTURE` from the launch/activate capture
      path (keep it only if a missing-identity capture still needs a seam) and
      re-capture `docs/captures/t14-dock-activation*.png` with the real
      injected pointer.
- [ ] Update the T110g gotcha in `PROGRESS.md` and, if the arbitration rule
      is design-level, add a short note to ADR 0101 (or a superseding ADR).
- [ ] Tests: `ctest --test-dir build -R "tst_dock|tst_dockcore"`,
      `make qml-test`, `make e2e`, `make check` unchanged.

## Explicitly deferred

- Touch/pen and middle-click activation.
- Cross-output click routing.
- A pointer-driven end-to-end test at the compositor level (the QML/handler
  regression plus the real capture is the proof here).

## Design notes

- One activation entry point: any fix routes through `activateEntry` →
  `entryActivated` → `onDockEntryActivated`; do not add a second launch path.
- The compositor remains the pointer authority; production must never fake a
  tap (the fixture seam exists because of this bug — removing it is part of
  done).
- Prefer a QML-side fix when possible so `tst_dock.qml` can prove it without a
  live compositor; only touch the injection if the QML path is already correct.
