## Hand-off

**Landed (done).** Fractional-scale chrome is now sized per output and the
nested scale seam exists. ADR 0153.

- `compositor/src/backend/nested.rs` — `DRAGONFRUIT_NESTED_SCALE`
  (`backend::ENV_NESTED_SCALE`, `parse_output_scale`, default 1.0);
  `NestedData::ensure_tracker` rebuilds the `OutputDamageTracker` whenever the
  output's physical mode size or **scale** changes. This is the chrome-sizing
  fix: the tracker's static scale is what every render element's geometry is
  resolved with, so the old hardcoded 1.0 placed elements in physical pixels
  but sized them in logical pixels (the T-16.3a wallpaper top-left bug).
- `compositor/src/shell/mod.rs` — `df_output` `set_mode` / `set_scale` /
  `set_transform` now call `reconfigure_layers()`, so every chrome layer is
  re-configured for the new logical output geometry and reserved zones
  refresh.
- `compositor/src/render.rs` — `update_chrome_preferred_scale` sends each
  output's chrome surfaces the fractional `wp_fractional_scale`
  `preferred_scale`; `accepts_fractional_scale` keeps X11 windows off the
  fractional path (T-16.3a retained).
- `compositor/src/input/synthetic.rs` — new `query scale` report (per output:
  physical/logical/scale; per window/chrome: logical and physical rects, and
  the surface's attached buffer scale/size).

**Deviation from the plan.** The scope's "per-surface viewport downscale" is
realized by the compositor mapping each surface's logical rect to physical
pixels with the output's fractional scale (Smithay's
`WaylandSurfaceRenderElement`), not by the compositor calling
`wp_viewport.set_destination` (that is a client-owned request; a compositor
cannot set it for a client). Empirically Xwayland derives its root window from
the output's **logical** size and renders its buffers at the logical size
(`buffer_scale` 1), so a fractional output scale composites X11 content at
`logical * scale` physical pixels without double-scaling. `docs/xwayland-scaling.md`
and ADR 0152's update record this; the old "integer-scaled buffer downscaled"
description was inaccurate.

**Follow-up (shell-side, not in this slice).** The shell's hand-rolled Wayland
client renders QML chrome offscreen at device pixel ratio 1 and does not bind
`wp_fractional_scale` / `wp_viewporter`, so it ignores the compositor's
preferred scale and its chrome is upscaled at a fractional output scale (the
"blurry chrome" half). The compositor half is done. See PROGRESS.md
Follow-ups.
