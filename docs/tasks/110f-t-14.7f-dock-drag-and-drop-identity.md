## Goal

Dropping onto the Dock is predictable and looks right: an app drag shows that
app's real name and icon while hovering and opens the gap with that identity;
files show what will happen per target (open with the app, move to Trash, move
to Downloads); a successful drop pins with the correct app-index identity; and
failures surface as notices instead of log lines.

## Current behavior (investigated, T101 era)

- During a drag the Dock knows only "app vs files"; the payload is read at
  drop, so the open gap is a generic translucent square and there is no
  name/icon feedback. A `.desktop` drag shows nothing identifiable until after
  the drop.
- App-alias drops pin correctly (id appended, then resolved through
  app-index), but duplicates silently do nothing.
- File/Trash/Downloads drops resolve through `dockdrops`, but Trash and
  Downloads failures only `qWarning()`; the user sees nothing.
- `dockdrops` already classifies app aliases vs files and supports
  spring-loading the Downloads stack.

## Scope

- [ ] Read the drag payload at **enter** (not only at drop) in
      `ShellProtocol`: start the receive for
      `application/x-dragonfruit-app`/`text/uri-list` when the drag enters the
      Dock, cache the parsed payload, and reuse it at drop (a data offer may be
      read once). If the read has not finished by drop, finish it
      synchronously/by the existing notifier before resolving — never drop a
      payload that is still in flight.
- [ ] Resolve the app identity during enter from `m_index` (desktop id → name +
      `iconPath`) and pass it through `beginExternalDrag`: app drags show the
      real tile + name in the open gap; file drags show the file count (and the
      first file's name for a single item).
- [ ] Target affordances while hovering:
      - app entry → app icon/name + "Open with" hint;
      - Trash → "Move to Trash", disabled/dimmed when `trashAvailable == false`;
      - Downloads stack → "Move to Downloads" (spring-load unchanged);
      - empty Dock/divider → no-op (no highlight).
- [ ] Duplicate pin: when the dragged app is already pinned, do not append;
      give visible feedback (brief highlight/return animation) instead of a
      silent no-op.
- [ ] Failures become user-visible: a failed launch, an unavailable Trash, or
      a failed move into Downloads raises the existing Dock notice path
      (`raiseDockLaunchFailure`/notification client); per-item partial failure
      is summarized, never a crash.
- [ ] Verify multi-file semantics: dropping N files on an app is one launch
      with all arguments (`%F`/`%U` via `buildLaunchCommand`); on Trash trashes
      all; on Downloads moves all; keep the existing unit coverage and add the
      multi-file case if missing.
- [ ] Tests: `tst_dock.qml` for the identity ghost, target affordances, and the
      duplicate-pin feedback; `tst_dockcore` for cached-payload parsing and the
      duplicate/resolved-identity cases; keep the compositor DnD conformance
      green.
- [ ] Capture `docs/captures/t14-dock-drops.png` (app ghost, file→app,
      file→Trash) and the `PROGRESS.md` note.

## Design notes

- One payload read per drag: cache on enter, consume on drop; never request the
  same mime twice.
- The ghost and target affordances are presentation only; `dockdrops` remains
  the single decision point for what a drop does.
- A failed identity resolution degrades to the existing generic tile + raw
  identity, never a crash (`legacy/10-dock.md` FR-7).
- Keep the app-index resolution on the shell side; QML receives resolved
  `name`/`iconPath` only.

## Hand-off

**Landed.** Drag payloads are read once at drag *enter*
(`ShellProtocol::beginDndRead`, cached by `parseDockDropPayload`) and reused at
drop (`ensureDndPayloadReady` does a bounded synchronous drain if the source is
still writing); the new `dockExternalDragPayload` signal gives the controller
the classified payload, which resolves the app alias through `m_index` to
`name`/`iconPath` and pushes it to the Dock's ghost. `Dock.qml` shows the app
tile + name in the open gap, a per-target affordance capsule
(`dockDropAffordance`: "Open with X"/"Move to Trash"/"Trash unavailable"/"Move
to Downloads"/"Add to Dock"), and a duplicate alias drop calls `flashPin`
instead of silently appending. Trash-unavailable, partial-trash, and
partial-Downloads failures call `raiseDockNotice` (new sibling of
`raiseDockLaunchFailure`). Multi-file drops stay one launch with all args / one
move or trash of every path.

**Contract for later tasks.** Enter-time read is the single receive; never call
`wl_data_offer_receive` again at drop. Identity stays shell-side; QML receives
only `name`/`iconPath`/count. `DF_DOCK_DROP_FIXTURE`
(`app`/`file-app`/`file-trash`) is a capture-only seam.

**Deviation / honest gap.** The required live visual check
(`make dock-drops-capture`, `docs/captures/t14-dock-drops.png`) uses the
`DF_DOCK_DROP_FIXTURE` presentation seam rather than a real drag source: the
harness has no reusable external DnD source client, and `make demo` runs
headless-scripted. The production path for the Dock presentation, identity
resolution, duplicate flash, and notices is what the fixture drives; the
compositor's `client_drag_and_drop_reaches_a_chrome_surface` still proves the
offer/receive plumbing. A scripted DnD source for an end-to-end capture is
recorded in `docs/PROGRESS.md` "Follow-ups".

**Tests run (repo root).** `ctest --test-dir build -R "tst_dock$|tst_dockcore"`
— green; `ctest --test-dir build --output-on-failure` — 53/53; `make e2e` —
green. `make check` unchanged (still stops at the pre-existing

**T-15.1a must know.** `dockdrops` is still the single drop decision point
