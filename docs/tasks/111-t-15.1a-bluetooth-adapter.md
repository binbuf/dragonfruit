## Hand-off

**State: done.** The BlueZ Bluetooth adapter landed in a new crate,
`dragonfruit-bluetooth` (`services/bluetooth`, workspace member), behind the
shared adapter contract. No shell wiring (T-15.1b renders it; the status-bridge
host is T-15.16).

What landed:

- `src/source.rs` — raw `BluetoothData`/`BluetoothAdapterData`/
  `BluetoothDeviceData`, `BluetoothOutcome` (`Accepted`/`Denied`/`Absent`/
  `Failed`), the `BluetoothSource` transport seam, and `MockBluetooth`
  (fixture-driven, with `kill`/`restart` and `deny_writes`/`fail_writes`).
- `src/model.rs` — `BluetoothController` (re-exported model name) and
  `BluetoothDevice`, plus `BluetoothSnapshot`: picks the controller, keeps only
  its devices, orders them connected/paired/name, derives
  `powered`/`discovering`, the `bluetooth`/`bluetooth-disabled` glyph, the
  label, and each device's 0–100 signal fill (BlueZ RSSI 0 = unknown).
- `src/bluez.rs` — `DbusBluez`, the live source: one
  `ObjectManager.GetManagedObjects` at `/` on the system bus reads every
  `org.bluez.Adapter1`/`org.bluez.Device1` object and decodes the property maps
  directly; writes are `Properties.Set` of `Powered`, `Start/StopDiscovery`,
  `Pair`, `Connect`/`Disconnect`. `org.bluez` absent is `Ok(None)` (absence);
  a polkit refusal is `BluetoothOutcome::Denied` (classified by the BlueZ/
  policykit error names and message).
- `src/adapter.rs` — `BluetoothAdapter<S>`; `refresh()` is the only daemon read;
  the four writes are explicit and do not invent a snapshot. A write against an
  absent daemon moves the state to `Unavailable`.
- Tests: 30 lib + `tests/read_path.rs` (9). Acceptance
  `the_fixture_renders_the_adapter_and_devices`,
  `an_absent_bluez_hides_the_item_and_never_errors`,
  `a_running_daemon_with_no_controller_has_nothing_to_show`,
  `a_present_but_unreadable_daemon_is_visible_and_inert`,
  `a_daemon_restart_resubscribes_and_resyncs`,
  `discovery_and_pairing_are_explicit_writes_that_do_not_invent_a_snapshot`,
  `a_denied_write_is_reported_and_the_read_state_stays_live`,
  `the_adapter_reads_once_per_refresh_never_in_a_poll`, plus a live-read smoke
  test. Fixture `tests/fixtures/bluez-office.json`.
- `Makefile` — `make e2e` runs `cargo test -p dragonfruit-bluetooth`.
- Docs — `07-system-integration.md` "The Bluetooth path (T-15.1a)"; ADR
  `0117-bluetooth-adapter-absence-and-write-outcomes.md`.
- Capture — `docs/captures/t15-1a-bluetooth-adapter.png` (this unit has no
  surface of its own; the nested demo was launched with the new crate in the
  workspace and the desktop renders).

Decisions / deviations:

- **No blanket read-only degradation on a polkit denial.** Unlike the Wi-Fi
  join path (ADR 0027), a Bluetooth denial is per-request (power/pair are
  polkit-authorized, discovery/connect are not), so the adapter returns the
  denial and keeps reads live. Recorded in ADR 0117.
- The adapter also models discovery and connection writes, because the track
  demo is "discover, pair, connect" and no later task owns them (T-15.1b is
  UI only).
- The live D-Bus source is compile-checked but not exercised in CI; the tested
  contract is the fixture-driven seam, mirroring the other adapters.

Live visual check: `make demo` nested on the host Wayland session, captured
with `spectacle -b -n -f` to `docs/captures/t15-1a-bluetooth-adapter.png`.
Verdict: the desktop renders (3840x2160, 468 614 unique colours; the demo log
shows the menu bar, Dock, notification banner, OSD, chooser, screencast, and
polkit surfaces configured, and a clean teardown). The vision tool returned
