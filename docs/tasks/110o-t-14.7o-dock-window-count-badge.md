## Goal

An app entry with two or more windows shows a small count badge on its icon
(capped at `9+`), so window grouping is visible at a glance; zero/one-window
entries show nothing. Attention-colored when the app demands attention.

## Context (read first)

- `shell/dock/DockEntry.qml` — the existing badge patterns: `statusBadge`
  (failure/missing/Trash-unavailable) and `stackBadge` (Downloads new items,
  `~374-392`). `badge`, `windowList`, `attention`, `stateLabel`,
  `tooltipLabel` all already exist.
- `shell/dock/DockGlyph.qml` — icon geometry; a badge sits at the tile's
  top-right corner with a token inset.
- `design-system/tokens/tokens.json` — `component.dock.*`; add a
  `windowBadge` group (size, font, inset, colors) or reuse existing badge
  values.
- `shell/src/dockprojection.{h,cpp}` / `dockmodel.{h,cpp}` — entries already
  carry `windowList`; a count can be derived in the shell (preferred, so the
  pure model owns it) or in QML.
- `shell/dock/Dock.qml` `tooltipLabel` — already says `"<name> — N windows"`;
  do not duplicate that logic.
- Reference behavior only (GPL, never copied): `WindowCountBadge.qml` in
  `~/repos/punchi-dock-remastered` shows a count when `count >= 2`, caps at
  `9+`, lets the user pick the corner, and uses an attention color. We use one
  token-defined corner.

## Current behavior (investigated, T110 era)

- A grouped entry looks identical to a single-window entry; only the tooltip
  (after a dwell) reveals the window count, and the chooser only appears on
  click.

## Scope

- [ ] Derive the window count in the shell projection/model (`windowList`
      length) and expose it on the entry (a `windowCount` field) so the pure
      model stays the source of truth; keep `badge` for app-provided counts.
- [ ] `DockEntry.qml`: render a count badge when `windowCount >= 2` and no
      app-provided `badge` is present; cap the label at `9+`; position and size
      from tokens; use the attention color when `attention` is true.
- [ ] Do not collide with the status badge (failure/missing) or the stack
      badge; a failure state wins (no count), and folders/Trash never show a
      window count.
- [ ] Accessibility: the entry's accessible name already carries the state via
      `stateLabel` — keep it; the badge is presentational and must not
      double-announce. Update `stateLabel`/`tooltipLabel` only if the count is
      missing.
- [ ] Motion: the badge fades in with `motion.focus`; reduced motion is
      instant.
- [ ] Tests: `tst_dockcore` for the derived count; `tst_dock.qml` for show at
      `>= 2`, hide at `0/1`, the `9+` cap, attention color, and the
      failure/stack precedence.
- [ ] Capture `docs/captures/t14-dock-window-badge.{light,dark}.png` and the
      `PROGRESS.md` note.

## Explicitly deferred

- General app-provided badges (app-index/notification service ownership;
  legacy T-10 §10) — the `badge` field stays but no producer lands here.
- User-configurable badge corner/opacity (tokens own it).
- Notification badges (→ T-11).

## Design notes

- One badge per entry. Precedence: status (failure/missing/Trash-unavailable) >
  app badge > window count > none.
- A pinned app that is not running has zero windows; no badge.
- A minimized-only app still counts its windows (the running indicator stays),
  matching legacy T-10 §10.
- Keep the count in the pure projection so the Dock's model tests cover it; the
  QML only formats `9+`.
