## Hand-off

What landed: the read-only battery item is live end to end. The bridge host
(`services/system-status`) now owns a `PowerAdapter` and serves a third
interface, `org.dragonfruit.SystemStatus1.Battery` (`State()`/`Refresh()` only;
no write), with `battery_view` JSON carrying `present`/`percent`/`level`/
`charging`/`label` and the two hidden cases. The shell decodes it in
`SystemStatusModel`, draws it in the new `BatteryMenu.qml`, and hides it both
when UPower is absent and when the machine has no present battery. The status
row is keyboard-accessible: Left/Right move a focus ring across available
slots, Return/Space opens the selected popover, Escape closes. `--placeholders`
is deleted from the shell CLI and the dev tool; the fixture client is now
selected with `DF_STATUS_FIXTURE=1` (headless/capture only), and the demo app
menu is kept for T-14.7.

Tests: `cargo test -p dragonfruit-system-status` (11 lib + 6 integration),
`make qml-test` (18/18, incl. new `tst_menubar` and `tst_statusmodel` battery
cases), `make e2e` exit 0. Capture: `bash scripts/capture-status-menus.sh`
produces `docs/captures/t07.5b-battery.png`; vision verdict — "82% charging",
bolt glyph, "1:30 until full", read-only, no stray artifacts.

Deviations / decisions: the dev tool does not start `dragonfruit-system-status`
(a real systemd/session unit owns it at packaging time; starting it from the
dev tool risks name conflicts and stray-process false positives). So a live dev
session shows the honest absent-daemon state until the host runs; the capture
script uses `DF_STATUS_FIXTURE=1` to render the fixture battery. Bluetooth is
no longer faked (its adapter is T-15).

For T-07.6: validate the absent-daemon matrix against the host and wire the
daemon change signals; do not poll. The battery read path never writes.
