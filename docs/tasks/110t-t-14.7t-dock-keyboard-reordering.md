## Goal

With the Dock keyboard-focused, `Ctrl+Shift+Left/Right` (Up/Down on a vertical
Dock) moves the focused pinned entry one slot, writing the new order through the
existing single-writer `dock.pinned` path — so the Dock's reorder affordance is
not pointer-only.

## Context (read first)

- `shell/dock/Dock.qml` — `Keys.onPressed` keyboard model
  (`moveKeyboardFocus`, `activateEntry`, `beginKeyboardNavigation`), and the
  drag-reorder persistence path: `currentPinnedIds()` → `pinnedOrderChanged` →
  shell writes `dock.pinned`. `appEntries`, `pinnedCount`, `appSlot()` define
  the ordered pinned region.
- `shell/src/dockmodel.{h,cpp}` — pure pin-list helpers; add the keyboard
  reorder here so it is unit-tested without QML.
- `shell/src/shellcontroller.cpp` `onDockPinnedOrderChanged` — the single writer
  (do not add a second path).
- `shell/tests/tst_dock.qml` — existing keyboard-nav and drag-reorder cases.
- Legacy [10-dock.md](../tasks/legacy/10-dock.md) §12 explicitly deferred
  keyboard reordering; §20 listed it as an accessibility enhancement.
- Reference behavior only (GPL, never copied): `DockItem.qml` in
  `~/repos/punchi-dock-remastered` uses `Ctrl+Shift+Arrow` (Up/Down on vertical)
  and documents it in the accessible description.

## Current behavior (investigated, T110 era)

- Keyboard focus can move between entries and activate them, but the pinned
  order can only be changed by pointer drag.

## Scope

- [ ] Pure helper (`dockmodel`): move the pinned id at index `i` to `i + delta`,
      clamped to the pinned region (0…pinnedCount-1), returning the new ordered
      list; no-op at the ends. Unit-tested.
- [ ] `Dock.qml` `Keys.onPressed`: `Ctrl+Shift+Arrow` (axis-aware, matching the
      Dock position) calls the helper, keeps the moved entry focused, and emits
      `pinnedOrderChanged` with the complete ordered pinned id list. Do not
      touch temporary/recent, minimized, stack, or Trash entries.
- [ ] Accessibility: expose the chord in the Dock entry's accessible
      description/help and announce the move (the focused entry's position). Do
      not steal the chord when the Dock is not keyboard-focused.
- [ ] Reduced motion: reordering is a discrete layout change; no new animation
      is required (reuse the existing reorder settle where it exists).
- [ ] Tests: `tst_dockcore` for the helper (bounds, no-op, full list);
      `tst_dock.qml` for the chord moving the focused entry, focus retention,
      axis-awareness, and that only `dock.pinned` is affected.
- [ ] Capture `docs/captures/t14-dock-keyboard-reorder.png` (focus ring on the
      moved entry) and the `PROGRESS.md` note.

## Explicitly deferred

- Keyboard reordering across regions/outputs (pinned region only).
- A keyboard "remove from Dock" / "pin" command (a separate accessibility unit).
- Touch reordering.
- Optimistic no-model-reset reorder: the known T-14.7c follow-up
  (`docs/PROGRESS.md`) still applies to both pointer and keyboard reorder; if it
  lands, this unit inherits it — do not fix it here.

## Design notes

- `dock.pinned` is written by settingsd alone; the Dock emits the full ordered
  list, exactly as the drag path does. Reuse `pinnedOrderChanged`; do not add a
  second signal.
- The helper is axis-independent (it operates on the pinned list); only the key
  mapping is axis-aware.
- A move at the boundary is a no-op, not a wrap.
- Keep the focus ring on the moved entry so repeated chord presses reorder
  continuously.
