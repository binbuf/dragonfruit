## Goal

Make settingsd restartable with no lost writes and document every key's owner and consumer.

## Scope

- Kill -9 then restart: compositor and shell re-sync; a change made while down is not silently applied.
- Key schema documented in-repo with owner and consumer for each key.
- Commit the scripted D-Bus flip capture.

## Explicitly deferred

## Hand-off

**Landed.**

- **Key schema in-repo.** `docs/settings-keys.md` — every key's D-Bus type,
  default, constraints, owner, consumer, plus a consumer map and the
  restart/resync contract. `services/settingsd/tests/schema_doc.rs` parses the
  table and fails if a key, type, default, owner, or consumer drifts from
  `services/settingsd/src/schema.rs`. `dragonfruit-settingsd --print-keys`
  remains the terminal view.
- **Kill -9 / restart, no lost write, resync.** Working end-to-end over a real
  private session bus: `services/settingsd/tests/restart.rs` spawns the actual
  `dragonfruit-settingsd` binary (`CARGO_BIN_EXE_…`), sets keys, `SIGKILL`s it,
  asserts the name is released, changes the durable file while it is down,
  restarts it, and asserts `GetAll` returns both the pre-kill writes and the
  while-down change.
- **Shell resync — real bug fixed.** `shell/src/settingsclient.{h,cpp}` now
  watches `org.dragonfruit.Settings1` with a `QDBusServiceWatcher`. The old
  `QDBusConnectionInterface::serviceRegistered`/`serviceUnregistered` path only
  fires for a connection's **unique** name, so the shell never re-synced after
  a restart of a settingsd owned by another process (it resynced once from the
  constructor's `GetAll`, then never). The live capture caught this; the
  `dbus-run-session` probe confirmed only unique names emit those signals.
  Do not replace the watcher with the interface signals.
- **Capture.** `scripts/capture-settingsd.sh` + `make settingsd-capture`
  produce `docs/captures/t08-settingsd.{png,mp4,txt}`,
  `-before-dark.png`, `-after-light.png`, `-down.png`, `-restart.png`.
  The transcript `t08-settingsd.txt` records the D-Bus calls and the persisted
  file. Raw pixels: menu bar `(255,255,255)` after the light flip, unchanged
  after `kill -9`, back to `(45,37,52)` on restart (the while-down file value);
  the Dock region differs between the `dock.size` 0.75 and 0.35 frames.

**Commands that work** (repo root; `make` sets the toolchain env):

- `cargo test -p dragonfruit-settingsd` — restart + schema_doc + session_bus all
  green.
- `ctest --test-dir build -R tst_settingsclient --output-on-failure` — green;
  the restart case serves the fake daemon from a **separate** bus connection so
  it exercises the remote (realistic) path.
- `make e2e`, `make lint`.

**Deviations / notes.**

- The `docs/captures/t08-settingsd.*` stills were captured under
  `SETTLE=9` on the development host; the transcript embeds the scratch
  `XDG_CONFIG_HOME`, which is intentionally ephemeral.
- `tst_settingsclient`'s restart case is the closest headless guard for the
  watcher, but it still runs the fake service in-process (on a separate
  connection); a full separate-process Qt regression test would need the
  settingsd binary in the shell test target and was not added. The Rust
  `restart.rs` test is the separate-process half.
- `workspaces.count` still has no live compositor owner (unchanged from
  T-08.2c); it is documented as such in `docs/settings-keys.md`.

**For T-09 / T-10.** Bind Wave-1 panes and Files preferences to
`org.dragonfruit.Settings1` as documented in `docs/settings-keys.md`. Add a key
by extending `schema::KEYS` (bump `SCHEMA_VERSION`, set `since`), the mirrored
`settingsSchemaDefaults()` in `shell/src/settingsclient.cpp`, and
`docs/settings-keys.md` (the doc test enforces the last one). Never rename or
remove a v1 key.
