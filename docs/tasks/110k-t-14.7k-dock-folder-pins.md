## Goal

Dragging any folder onto the Dock pins it as a stack, exactly like macOS: the
folder lists its contents in the Dock popover, opens in Files, accepts files,
and persists across restarts. The Downloads stack becomes the same widget with
a default pin.

## Current behavior (investigated, T101 era)

- Only `~/Downloads` is a stack, fed by `DownloadsMonitor`; there is no way to
  pin any other folder, and a folder dropped on the Dock is a no-op (only a
  single `.desktop` pins).
- `dock.pinned` holds desktop ids only; there is no folder-path state and no
  settings key for it.

## Explicitly deferred

- Recursive/infinite folder stacks, grid/fan layouts (list popover only).
- File Stacks / arbitrary file pins; smart folders.
- Folder pinning from Files' own menus (could reuse the same key later).

## Design notes

- One directory-listing owner: `files-core`. The shell never opens/watches
  folders itself (the Downloads monitor is folded into this path).
- Folder pins are independent of app pins: a separate ordered key keeps the
  app pin semantics (`desktopId`) exact; the Dock renders folder pins in the
  right region beside the stack slot.
- Security: only absolute, existing local paths are persisted; a path that is
  not a directory is rejected with a notice.
- Settingsd remains the only writer; the Dock never persists locally.

## Hand-off

**Landed.** Any folder dropped on the Dock pins as a stack; it lists through
files-core, opens its popover, opens in Files, moves files in on drop, and is
removed by drag-out or the context menu. The Downloads stack is the built-in
first member of the same widget and model.

- **Key shape:** `dock.pinnedFolders` — `as`, ordered absolute paths, default
  empty, schema `SCHEMA_VERSION = 7` (`since: 7`), owner/consumer `shell/Dock`.
  Documented in `docs/settings-keys.md`. The Downloads path is intentionally
  *not* stored in the key; it is the always-present default member.
- **files-core seam:** `FolderStacks` (`shell/src/folderstacks.{h,cpp}`) lists
  through `files_core_list.h` (`df_files_begin`/`df_files_poll`), the same poll
  the chooser bridge uses. files-core does not expose its `FolderWatcher` over
  the shell C ABI, so change notification is a `QFileSystemWatcher` (notify
  only, never a reader). `moveFilesIntoFolder` is the shared move helper. See
  ADR 0104.
- **Drop path:** `dockdrops` classifies app alias | folder | files; a folder on
  the app region is `PinFolder`, files/folder on a stack are `MoveToFolder`
  (target id `__downloads__` or `folder:<path>`). The folder ghost is the stack
  silhouette + basename.
- **Remove path:** drag the tile off the Dock or Remove from Dock in the
  context menu; both emit and the shell writes `dock.pinnedFolders` through
  settingsd (the only writer).
- **What T-15.1a must know:** folder pinning from Files' own menus can reuse
  `dock.pinnedFolders` unchanged (write an absolute path list), and should route
  through the same `FolderStacks`/files-core listing; do not add a second
  directory reader. A later task should fold the live folder-pin count into
  `computeDockOverflow`'s `fixedCount` (still 2: Downloads + Trash).
- **Tests:** `cargo test -p dragonfruit-settingsd`; `ctest --test-dir build
  --output-on-failure` 53/53 (`tst_dock` 181, `tst_dockcore` folder cases);
  `make e2e`; `./scripts/gen-tokens.py --check`,
  `./scripts/check-design-tokens.sh`, `./scripts/check-no-capture-grab.sh`.
- **Capture:** `docs/captures/t14-dock-folder-pin.png` (`make
  dock-folder-pin-capture`; pinned + open panels). The nested live drag from
  Files was not exercised; the capture used the fixture's settingsd write path.
  Confirm the real drag in the human sign-off.
- **Deviations:** `downloadsmonitor.{h,cpp}` retired; `QFileSystemWatcher`
  retained as the change seam until files-core exposes its watcher; Downloads is
  not removable; the overflow clamp ignores extra folder pins.
