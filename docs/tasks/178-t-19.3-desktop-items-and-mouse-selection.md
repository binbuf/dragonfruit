## Goal

`~/Desktop` renders as an icon view on the desktop (label under each icon) and
responds to the mouse: click selects, Cmd/Shift click extends the selection,
rubber-band drag selects a region, and double-click opens. This is the **first
slice** of the macOS model where the file manager owns the desktop; it is the
groundwork for the full desktop-operations experience, deliberately scoped to
render + select + open.

## Reference UI/UX (macOS screenshots)

- Plain wallpaper with **grid-aligned icons**, label centered under the icon,
  regular weight, light appearance default.
- Idle / hover / selected states on each tile; the label may be two lines.
- Empty desktop is just background; a right-click on it offers desktop actions.
- Multi-select via drag (rubber band), Cmd-click, and Shift-click.

## Scope

- [x] **Compositor desktop layer.** Extend the compositor to composite a
      `background`-layer surface *below* windows and *above* the per-Space
      wallpaper, and route pointer (and, when its interaction mode asks,
      keyboard) input to it. A click on empty desktop clears window focus.
      `render.rs`/`chrome_surfaces` must stop skipping the desktop layer.
- [x] **Trust.** Extend the `df_core` launch-token admission so the Files
      desktop process may create a `background`-layer `df_layer_surface`;
      `bind` from any other client is still refused (add the refusal case).
- [ ] **`dragonfruit-files --desktop`.** Add the flag (`FilesArguments`), start
      as a borderless desktop-layer surface over `~/Desktop` (xdg-user-dirs),
      and keep it independently killable/restartable: killing it leaves the
      browser and session alive, and vice versa.
- [ ] **Desktop icon view.** Reuse `FilesIconView`/`FilesDirectoryModel` for a
      grid over `~/Desktop` with label-under-icon and hover/selected states.
- [x] **Mouse selection.** Click selects; Cmd-click toggles; Shift-click
      extends; **rubber-band** drag over empty background selects the enclosed
      tiles; double-click opens (directory → a Files window at that path; file →
      the default handler). Selection is the Files shell's set of stable node
      ids. (View + shell logic; shared by the future desktop surface.)
- [ ] **Minimal background context menu.** Right-click on empty desktop offers
      `Open in Files` and `New Folder` (the latter via the existing `files-core`
      ops engine); anything richer is deferred.
- [ ] No polling while idle: the listing is monitor-driven through
      `files-core`, exactly like a Files window.

## Out of scope

- Desktop mutations beyond `New Folder`: inline rename, drag-to-Trash, drag
  between desktop and windows, spring-loading.
- The full context-menu engine (→ follow-up slice of legacy T-19).
- Desktop Reveal exposing icons; selection/focus transfer between the desktop
  surface, chrome, and windows (→ follow-up).
- Per-output/multi-monitor desktop grid policy (decide and document before that
  slice; one logical grid per Space is the current lean).
- Desktop widgets (not planned).

## Design notes

- **Slice boundary.** If this exceeds one session, split along the seams the
  harness can see: (a) compositor desktop layer + trust, (b) the
  `--desktop` process + listing, (c) mouse selection/rubber-band. The unit must
  still finish each slice with its tests green.
- The desktop is the file manager's, not the shell's: the shell keeps drawing
  only chrome and never renders desktop items.
- Selection is ids, never paths (matches Files); the model alone resolves a
  node id to a name/icon.
- Layer order is wallpaper → desktop layer → windows → chrome; assert it in a
  compositor unit test rather than eyeballing it.
- Reuse the ops engine for `New Folder` — no direct filesystem calls in the
  view.

## Hand-off

**Status: continue.** The compositor desktop-layer + trust slice and the
shared view-selection slice landed and the tree is green; the
`dragonfruit-files --desktop` process (compositor half of the feature) remains.

### What landed

- **Compositor desktop band.** `compositor/src/shell/layer.rs` adds
  `LAYER_BACKGROUND`/`LAYER_TOP`, `above_windows()`, `is_desktop()`, and the
  `StackBand` enum whose derived order is `Wallpaper < Desktop < Windows <
  Chrome`. `render::desktop_render_elements` emits `background` surfaces; the
  nested and DRM backends append it **between** window elements and wallpaper
  elements (front-to-back list), so the desktop composites below windows and
  above the wallpaper. `chrome_render_elements` keeps handling only
  above-window `top`/`overlay`.
- **Role-scoped trust.** `TrustedRole::may_create_layer` (shell ⇄ `top`/
  `overlay`, desktop-icons ⇄ `background`). `df_shell.get_layer_surface`
  refuses a wrong-band request with the same `ERROR_ACCESS_DENIED`/kill path
  as an untrusted bind. `provision()` now parses `[role:]hex` entries in
  `DRAGONFRUIT_LAUNCH_TOKENS`, mints `desktop:` entries as `DesktopIcons`, and
  writes `<socket>.desktop-launch-token` (also removed at teardown);
  `DRAGONFRUIT_DESKTOP_LAUNCH_TOKEN` is the single-token fallback.
- **Input / focus.** `input::chrome_under` now only hit-tests above-window
  layers; `input::desktop_under` is the fall-through after the window `Space`,
  so windows beat the desktop and the desktop beats empty space. A missing
  desktop surface yields `None`, i.e. exact pre-T-19.3 behavior.
  `focus_changed` treats only above-window chrome as chrome-preserving
  (`DfState::is_above_window_chrome_surface`), so focusing the desktop clears
  `active_window`; `chrome_has_keyboard_focus` also excludes the desktop so a
  desktop click is not immediately cleared as click-away.
- **Rubber-band selection (shared view).** `FilesIconView` paints a marquee over
  empty background, resolves the enclosed delegate rectangles to stable node
  ids (`enclosedIds`) and emits `marqueeSelected(nodeIds, modifiers)`; the
  pointer path and the test seam share `rubberBandSelect`. `FilesShell`
  `selectMarquee` replaces / Cmd-toggles / Shift-extends. Click, Cmd-click,
  Shift-click, the `activated` signal, and the band are QML-tested.
- **`--desktop` argument.** `FilesArguments::filesDesktopRequested` and
  `filesDesktopDirectory` (xdg-user-dirs via `QStandardPaths`, `$HOME/Desktop`
  fallback), unit-tested. The location parser already ignores `--desktop`.
- **Docs:** ADR
  [0168](../design/adr/0168-desktop-layer-and-role-scoped-layers.md); the track
  doc, `09-files.md` §Desktop icons, `02-compositor.md` §Private shell
  protocols.

### Deviations / decisions

- The desktop band is only `background` (0); the `bottom` layer (1) stays
  unimplemented and is aliased into the desktop band so it can never leak above
  windows. This is recorded in ADR 0168.
- Added `desktop:` role tags to `DRAGONFRUIT_LAUNCH_TOKENS` rather than a new
  list format, so existing bare-hex provisioning is unchanged.
- The `--desktop` flag is parsed but `main.cpp` does not yet branch on it; there
  is no desktop protocol client in `apps/files` (it has no Wayland dependency).
  Launching with `--desktop` today opens the normal browser window.
