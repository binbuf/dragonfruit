## Hand-off

### What landed

- `PresentationClock` owns an optional backend `VrrRange`, the last measured
  `last_interval`, the accepted `vrr_interval`, and a per-output `presentations`
  counter. `note_presented()` adapts the next deadline only when
  `VrrState::On` *and* a range is installed; an in-range interval becomes the
  next period, while an out-of-range interval (an idle gap, a too-fast
  completion) falls back to the nominal mode period. `vrr_report()` is
  `on` / `off` / `unsupported`; `On` without a range is `unsupported`. One
  measured interval never turns VRR on.
- `VrrRange` normalizes reversed bounds and rejects zero periods. The current
  range is the mode period (fastest end) to the refresh model's 24 Hz floor
  (`SLOWEST_PERIOD`); a real panel range can replace it through
  `set_vrr_range`.
- `DfState::output_vrr` carries the backend state. `set_output_vrr()` updates
  the schedule and the clock range; `refresh_for_output()` preserves the VRR
  state across the diagnostic refresh override. `on_output_mode_changed()`,
  `recompute_refresh_schedule()`, and output removal keep the map and clocks
  in sync.
- DRM connector bring-up queries `DrmCompositor::vrr_supported()` and enables
  VRR only for `VrrSupport::Supported` (no modeset). `RequiresModeset` and
  `NotSupported` keep the fixed period and report `off`/`unsupported`; nested
  and headless report `unsupported`. `df_output.vrr` reports the actual state
  instead of a hardcoded zero.
- `presentation stats` and `frame request` append `vrr`, the accepted
  interval, the range, `presentations`, and `last_interval_us`.
- Chrome frame callbacks remain on `post_repaint()` for every presented output
  frame and on `send_frame_callbacks()` for the no-damage callback path. The
  T188c capture proves the counter advances on presented nested frames.
- Mixed-refresh hooks: the pure test
  `frame_scheduler::tests::mixed_refresh_60_and_144_with_one_idle_and_one_animating`
  runs 60 Hz + 144 Hz with a third idle output; the synthetic-output harness
  accepts an optional refresh (`add ... [refresh_mhz]`), and the synthetic
  input harness accepts `animate-dummy-on <output> <ms>`.
- New capture `scripts/t21-vrr-mixed-refresh.sh` / `make
  t21-vrr-mixed-refresh`: nested 144 Hz single-output + shell (VRR report and
  chrome callbacks), headless 60 Hz + synthetic 144 Hz three-scenario mixed
  run, and a native `OPEN` artifact.
- Docs: ADR `0202-vrr-adaptation-and-mixed-refresh-evidence.md`,
  `docs/rendering.md` P4/R3.3, `docs/design/02-compositor.md`,
  `docs/design/STATUS.md` G-02/G-13, `docs/captures/README.md`.

### Evidence

`docs/captures/t21-vrr-mixed-refresh.txt` (PASS):

- Nested 144 Hz single output: `period_us=6944`, `vrr=unsupported`,
  `presentations` +12 during the Dock sweep, `chrome_frame_callbacks` 1 -> 4.
  The nested host throttles `submit()`, so `last_interval_us` is ~1 s; the
  derived period/VRR report is the single-output evidence, not cadence.
- Headless synthetic 60 Hz (`HEADLESS-1`) + 144 Hz (`MIXED-144`):
  - 144 Hz-only animation: 60 Hz delta 0, 144 Hz delta 48,
    `last_interval_us=7525`.
  - 60 Hz-only animation: 60 Hz delta 21, 144 Hz delta 0,
    `last_interval_us=17108`.
  - both animate: 60 Hz delta 21, 144 Hz delta 49.
  - after settling: both deltas 0; `animation=0 timer_armed=0`.
- `docs/captures/t21-vrr-mixed-refresh-native.txt` is an explicit `OPEN`
  artifact: this host is already a native Dragonfruit session with one
  connected output (`card1-DP-1`), so restarting its compositor for a 60+144
  run would end the session. Rerun on a free two-output seat with
  `DRAGONFRUIT_T21_NATIVE=1 make t21-vrr-mixed-refresh` and attach the DRM
  `presentation stats` lines.

### Deviations

- The VRR range is the scheduler's supported range (mode period to 24 Hz), not
  an EDID FreeSync range; libdrm exposes VRR capability but not the panel's
  min/max through Smithay's connector info. The clock never infers a range
  from measurements.
- DRM auto-enables VRR for `VrrSupport::Supported` connectors. The private
  `set_vrr` request remains an ack; there is still no Displays-pane policy.
- Native mixed-refresh is `OPEN`: this host has one connected DRM output and
  the live native session owns it. The synthetic 60+144 trace is not native
  proof and is labelled as such.
- The nested rail's `submit()` completion is throttled by the host, so it is a
  single-output correctness trace only. Chrome callbacks are driven by a real
  shell Dock sweep, and the capture polls `animation=0 timer_armed=0` before
  taking the settled sample.
- `animate-dummy-on` is test plumbing only; normal sessions still use the
  unscoped `animate-dummy` path and never set `dummy_animation_output`.
- Unrelated working-tree files `docs/dock-learnings.md` and the matching
  `docs/INDEX.md` entry were left untouched; they are not part of this task.
