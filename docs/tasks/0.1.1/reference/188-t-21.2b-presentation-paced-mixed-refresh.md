## Goal

Drive animation frames from actual presentation timing, per output, instead of
one global timer. A 60 Hz output must not throttle a 144 Hz output; a 60 Hz
animation on a 144 Hz panel must be reported against 144 Hz deadlines; an idle
output must produce no presentation samples and no damage. VRR is used only
where the backend actually exposes it, never claimed otherwise.

- `compositor/src/backend/drm.rs` — `render_pending()` renders every output
  when global `state.needs_redraw` is set; `frame_finish()` has the real vblank

## Scope

- [ ] Add a per-output presentation clock:
  - `last_presented`, `next_deadline`, `period`, `refresh_hz`, `vrr`,
  - `note_presented(timestamp)` from `frame_finish()` / nested `submit()`,
  - `is_due(now)` and `time_until_due(now)`.
- [ ] Replace the single global `needs_redraw` gate for animation frames with
  per-output frame requests:
  - urgent requests (input, client commit, chrome commit, resize) render
    immediately,
  - animation requests render each output when its own deadline is due,
  - a global scene change may mark all outputs urgent, but a 144 Hz animation
    tick must not force a 60 Hz output to present every 6.94 ms.
- [ ] Arm the animation timer from the earliest due output deadline; after a
  presentation, update that output's clock and re-arm. Do not busy-loop or
  render a settled output.
- [ ] In `frame_finish()`, record the real vblank interval (already done),
  update the presentation clock, and count a missed deadline at 1.5× the
  output period (existing rule). Include `refresh_hz` in the summary.
- [ ] In the nested backend, use the `submit()` completion time as the
  presentation timestamp when no platform vblank is available; keep the
  fixed-period fallback if it is not available.
- [ ] VRR:
  - if the backend exposes a VRR state and a variable presentation interval,
    adapt the next deadline within the output's supported range,
  - otherwise report `vrr=unsupported` and keep the fixed period,
  - never infer VRR from a single short interval.
- [ ] Send chrome frame callbacks on every presented output frame and on the
  no-damage callback path, so T185/T186's QML pacing follows the same clock.
- [ ] Add a test hook for mixed-refresh scheduling (two synthetic outputs or a
  pure scheduler test): 60 Hz + 144 Hz, one idle, one animating. The pure
  scheduler must be testable without DRM.

## Design notes

- Animation progress is still monotonic elapsed time. Per-output pacing
  changes **when** a frame is presented, never the tween's duration.
- A 60 Hz output that is animating should present at ~16.67 ms intervals even
  while a 144 Hz output presents at ~6.94 ms. Do not render both at 144 Hz and
  call it mixed refresh.
- The deadline is the output's period, with a small submit margin if the
  backend exposes one. Do not use half the period as a "safe" budget; that
  silently doubles the required GPU throughput.
- An idle output must not be woken by another output's animation. The
  per-output request set is the mechanism; `state.needs_redraw` must not be the
  only gate.
- `DrmCompositor::queue_frame()` must be called exactly once per output-frame;
  the scheduler must not queue an empty retry that fights the next deadline.
- Frame callbacks are presentation feedback, not a second render loop. Send
  them after the frame is queued/presented; never render from inside the
  callback on the compositor thread.
- Nested is not mixed-refresh proof. A nested 144 Hz simulated run can prove
  the single-output interval, but the 60+144 claim needs a real two-output
  session or a recorded `OPEN` marker.

## Acceptance criteria

- [ ] The pure scheduler test proves: 60 Hz + 144 Hz animating outputs present
  at their own periods; a 60 Hz output does not present at 144 Hz; an idle
  output receives no animation frames.
- [ ] A simulated single-output run at 60/120/144/240 Hz records the expected
  interval and `missed` counts; a 60 Hz animation on a 144 Hz output is not
  reported as healthy.
- [ ] `presentation stats` reports p50/p95/p99, `missed`, `budget_us`, and
  `refresh_hz` per output; a settled desktop produces zero new samples.
- [ ] `make idle-trace` still shows zero animation frames, zero damage, and
  zero client wakeups while idle.
- [ ] On real hardware, a 60 Hz + 144 Hz mixed setup (or the closest available)
  shows the fast output keeping its cadence while the slow output animates;
  if unavailable, the report is explicitly `OPEN`.
- [ ] Chrome frame callbacks advance with presented frames on both backends;
  no callback storm while idle.
- [ ] No double-damage, clock drift, or output starvation after 5 minutes of
  mixed animation.
