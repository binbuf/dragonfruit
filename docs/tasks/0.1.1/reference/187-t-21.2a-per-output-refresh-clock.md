# T187 — T-21.2a Per-output refresh model and animation clock

| | |
|---|---|
| **Track** | T-21 — Presentation foundation |
| **Release** | v0.1.1 |
| **Depends on** | T183 |
| **Blocks** | T188, T189 |
| **Hardware** | no (test hook covers 60/120/144/240; native in T188/T191) |

## Goal

Replace the global 16 ms animation/degrade constant with a per-output refresh
model. The compositor learns each output's real mode period, derives a
deadline, drives the animation clock from the fastest active output, and
selects the degrade budget from that deadline instead of assuming 60 Hz. A
144 Hz panel is judged against 6.94 ms, not 16 ms.

This task builds the model and wiring; actual presentation-paced per-output
scheduling is T188.

## Context (read first)

- `compositor/src/animation.rs` — `FRAME_INTERVAL` (~:32) and
  `AnimationClock::frame_interval()` (~:226) return the fixed 16 ms interval.
- `compositor/src/input.rs` — `schedule_animation_timer()` (~:1018) arms a
  `Timer::from_duration(FRAME_INTERVAL)`; `poll_animations()` re-arms it.
- `compositor/src/window/degrade.rs` — `DegradeController::new()` defaults the
  budget to `FRAME_INTERVAL` (~:354); `ENV_FRAME_BUDGET_US` is the override.
- `compositor/src/backend/drm.rs` — `frame_finish()` already derives
  `frame_duration` from `Output::current_mode().refresh`; `render_pending()`
  is the on-demand render loop.
- `compositor/src/state.rs` — `PresentationStats` (per-output vblank ring,
  `budget_us`, `missed`) and `dump_stats`.
- `docs/rendering.md` — R3.1 (per-output deadline).
- `docs/design/architecture-audit-native-rendering.md` — §9.4 (60 Hz constants
  on a 144 Hz output).
- `docs/design/STATUS.md` — G-02.

**Important unit:** Smithay's `Mode.refresh` is **millihertz** (`143999` is
143.999 Hz), not Hz. The period is `1e9 / refresh_mhz` nanoseconds (or
`1_000.0 / refresh_mhz` seconds).

## Scope

- [ ] Add a pure refresh model (new module or `state.rs`; no renderer
  dependency):
  - `OutputRefresh { refresh_mhz, period, deadline, source, vrr }`,
  - `RefreshSchedule` keyed by output name with `update(output, mode)`,
    `remove(output)`, `fastest_period()`, `for_output(name)`,
  - fallbacks: no mode / zero / invalid refresh → 60 Hz; clamp to a sane range
    (e.g. 24–500 Hz); preserve the exact mode period when valid,
  - VRR state: `Unknown`/`Off`/`On` field for T188; this task does not
    implement VRR behavior.
- [ ] `AnimationClock` owns the current tick interval (set from
  `RefreshSchedule::fastest_period()`) instead of returning `FRAME_INTERVAL`.
  `schedule_animation_timer()` uses that interval; `poll_animations()` re-arms
  with the current interval.
- [ ] Recompute the schedule on output add/remove, mode change, scale/transform
  change, hotplug, and resume. Re-arm/cancel the animation timer if the
  fastest period changes while an animation is live.
- [ ] Update `DegradeController`'s budget from the current schedule deadline
  (fastest active output for now; per-output/per-role selection is T189).
  Keep `DRAGONFRUIT_FRAME_BUDGET_US` as a test/diagnostic override and record
  when it is active.
- [ ] Append `refresh_hz` (and, if useful, `source=mode|fallback|override`) to
  the `presentation stats` line without renaming existing fields. Update
  `PresentationStats::record()` to carry the refresh value it already receives.
- [ ] Add a test-only refresh override (e.g. `DRAGONFRUIT_REFRESH_HZ`) or a
  synthetic output mode so nested/headless tests can exercise the
  60/120/144/240 table without hardware. The override must be absent from
  normal sessions.
- [ ] Keep animation progress on monotonic elapsed time. Do not replace 16 ms
  with a global 8 ms; the tick interval is derived, not hard-coded.

## Out of scope

- Per-output presentation deadlines, mixed-refresh rendering, and VRR behavior
  (→ T188).
- Per-role/per-output material floors (→ T189).
- Material cost (→ T190).
- Changing animation durations or design tokens.

## Design notes

- The clock still advances **one animation state per tick**. The tick rate is
  the fastest active output's period so a 144 Hz output is not throttled by a
  60 Hz output; T188 will gate each output's render by its own deadline.
- The schedule is policy, not a renderer. Keep it unit-testable with no
  `Output` handle; pass in name + mode refresh + optional VRR.
- A 60 Hz fallback is correct when a backend has no mode (headless/nested
  before a mode is known). Do not invent 144 Hz.
- Do not re-arm the timer on every frame if the interval did not change; the
  existing one-timer discipline and idle zero-wakeup guarantee must hold.
- `PresentationStats` is append-only: existing consumers parse named fields, so
  add `refresh_hz` at the end. A `budget_us` of 6944 and `refresh_hz=143.999`
  must agree.
- The degrade controller's 12/180 hysteresis is frame-count based; T189 will
  make it refresh-aware. This task only feeds it the right budget.

## Acceptance criteria

- [ ] Unit tests pin the period/deadline for 60, 120, 144, and 240 Hz
  (`16.67`, `8.33`, `6.94`, `4.17` ms within tolerance), invalid/zero
  refresh fallback, and mode-change replacement.
- [ ] The animation timer uses the derived interval: a simulated 144 Hz run
  steps at ~6.94 ms, not 16 ms; a 60 Hz run still steps at ~16.67 ms.
- [ ] The degrade budget follows the schedule (`budget_us` matches the fastest
  active output) and the `DRAGONFRUIT_FRAME_BUDGET_US` override is recorded.
- [ ] `presentation stats` includes `refresh_hz` and the value matches the
  output mode; existing fields keep their names.
- [ ] Idle behavior is unchanged: `make idle-trace` shows zero animation frames,
  zero damage, and zero client wakeups when nothing animates.
- [ ] No global 8 ms constant is introduced; the 16 ms constant remains only as
  a documented fallback/default.
