# T186 — T-21.1d GPU-backed chrome transport

| | |
|---|---|
| **Track** | T-21 — Presentation foundation |
| **Release** | v0.1.1 |
| **Depends on** | T185 |
| **Blocks** | T192 |
| **Hardware** | optional (nested GL is the first rail; native in T191/T192) |

## Goal

Remove the CPU readback from the shell's chrome path: render the QML scene with
Qt Quick's GPU renderer through `QQuickRenderControl`, export the rendered
frame as a `linux-dmabuf` buffer, and commit that buffer directly to the
compositor. The compositor imports it as a GPU texture, so an animated Dock
frame has **zero CPU readbacks and zero CPU-to-GPU copies** on a supported
driver. T185's pooled SHM path remains the fallback.

## Context (read first)

- T185 — `ChromeFrameProducer`/`ChromeSurface`, pooled SHM fallback, frame
  callbacks.
- `shell/src/shellprotocol.cpp` — surface creation and `commitTo()`; the new
  path needs a dmabuf commit variant, not a QImage variant.
- `compositor/src/state.rs` — `delegate_dmabuf!`, `DmabufState`, supported
  formats (`Abgr8888`, `Argb8888`); `init_dmabuf()` advertises
  `zwp_linux_dmabuf_v1` with feedback.
- `compositor/src/render.rs` — `chrome_render_elements()` imports the layer
  surface through Smithay's `WaylandSurfaceRenderElement`.
- `compositor/src/backend/drm.rs` — `DrmOutputElements::Chrome` and the
  `ImportDmaWl` bounds; dmabuf-backed chrome must composite through the same
  path as SHM chrome.
- `docs/rendering.md` — R2.3 (GPU-backed `QQuickRenderControl` or Qt Wayland
  path).
- `docs/design/architecture-audit-native-rendering.md` — §5 (why the current
  path is expensive) and §7 (renderer/import constraints).
- Qt 6.11: `QQuickRenderControl`, `QQuickRenderTarget`,
  `QQuickWindow::setGraphicsApi`, `QOpenGLContext`, `QOffscreenSurface`,
  `QOpenGLFramebufferObject`; EGL/GBM headers are in the toolchain.
- `protocols/` and the compositor's `linux-dmabuf` implementation.

## Scope

- [ ] Implement a `GpuChromeFrameProducer` behind the T185 abstraction:
  - create an OpenGL/RHI context and an offscreen surface,
  - create a `QQuickRenderControl` and a hidden `QQuickWindow`,
  - render the QML scene into a reusable FBO/`QQuickRenderTarget` once per
    requested frame,
  - use `QQuickRenderTarget::setDevicePixelRatio()` so QML layout stays
    logical while rasterization is physical (T184).
- [ ] Export the rendered FBO as a dmabuf:
  - create an EGLImage from the FBO texture,
  - export it with `eglExportDMABUFImageMESA` (or the platform-equivalent
    extension),
  - create `zwp_linux_buffer_params_v1` / `zwp_linux_dmabuf_v1` buffers with
    the negotiated format/modifier/stride/offset,
  - attach/commit the dmabuf-backed `wl_buffer` through a new
    `ShellProtocol::commitDmabufTo()` (or equivalent).
- [ ] Keep a small per-surface dmabuf buffer ring (2–3 buffers), returned by
  `wl_buffer.release`; recreate only on resize/format change.
- [ ] Synchronize correctly: use an EGL/GL fence or an explicit dmabuf sync
  path before the compositor samples the buffer. If only an implicit-sync path
  is available, record it as a limitation; do not race the compositor.
- [ ] Negotiate formats/modifiers from the compositor's dmabuf feedback; if no
  compatible format/modifier or EGL export is available, fall back to T185's
  pooled SHM path and report the reason in `chrome stats`.
- [ ] Add `DRAGONFRUIT_CHROME_GPU` (default **off** until T192/T193 accept it):
  `1` enables the GPU path, `0` forces the T185 fallback. Never make a failed
  GPU path a black surface.
- [ ] Evaluate Qt's Wayland platform plugin as an alternative in the ADR
  started by T183. The expected blocker is that the shell owns private
  `df_layer_surface` roles, not `xdg_toplevel`; record the evidence rather than
  assuming it.
- [ ] Apply the path to the Dock and menu bar first, then the popover/overlay
  surfaces; keep one code path for all chrome surfaces where possible.
- [ ] Keep the private layer protocol and surface roles unchanged; the shell
  must remain independently restartable.

## Out of scope

- Changing the compositor's material/blur architecture (→ T189, T190).
- Per-output refresh scheduling (→ T187, T188).
- A second UI renderer, Skia/Impeller/Flutter, or a custom QPA plugin.
- Multi-GPU cross-device sampling (existing fallback stays; T193 records it).

## Design notes

- The compositor already advertises `zwp_linux_dmabuf_v1` and imports dmabufs;
  do not add a private protocol or a compositor-side CPU upload fallback for
  the GPU path. If the import fails, fall back in the shell.
- The buffer must be in a format the compositor advertises (`Abgr8888` or
  `Argb8888` today). Alpha must be premultiplied; the material/blur expects
  translucent chrome.
- `QQuickRenderControl` does not own a platform window. Do not call
  `grabWindow()`; do not use `QQuickWindow::show()`.
- Use the shell's existing `wl_display` for the EGL platform display; do not
  open a second Wayland connection for the GPU context.
- Qt's render target may be multisampled; resolve to a single-sample texture
  before export unless the compositor/dmabuf path supports the sample count.
- Use one GL context per shell process, not per surface. FBOs/textures are
  per surface; the context is shared.
- A dmabuf buffer is owned by the compositor until `wl_buffer.release`. Keep
  the EGLImage/FBO alive until then; do not re-render into a busy buffer.
- Frame callbacks (T185) remain the pacing source; the GPU path changes the
  buffer type, not the pacing contract.
- The runtime flag must be visible in `chrome stats` (`path=dmabuf|shm`), and
  a fallback must say why (`no-egl-export`, `no-format`, `import-failed`, …).

## Acceptance criteria

- [ ] With `DRAGONFRUIT_CHROME_GPU=1` on a supported nested GL session, an
  animated Dock frame reports `path=dmabuf`, `grab_renders=0`, and **zero**
  CPU copy bytes/readbacks in `chrome stats`.
- [ ] The compositor reports `chrome_dmabuf_imports` advancing for chrome
  surfaces; no `chrome_shm_imports` for the converted surfaces.
- [ ] The Dock/menu bar/popover render correctly over live content (no black,
  stale, torn, or upside-down frames) through a full Dock sweep, menu open/
  close, popover open/close, and a window resize.
- [ ] Buffer-ring reuse is stable: no per-frame dmabuf/FBO allocation after
  warm-up; no use-after-free under rapid commits.
- [ ] `DRAGONFRUIT_CHROME_GPU=0` and an unsupported driver both fall back to
  the T185 pooled SHM path with a recorded reason; the fallback is visually
  identical.
- [ ] The shell still restarts cleanly after a kill and the private protocol
  is unchanged.
- [ ] The ADR records the chosen GPU path, the format/modifier/sync strategy,
  and why Qt's Wayland platform plugin was or was not used.
