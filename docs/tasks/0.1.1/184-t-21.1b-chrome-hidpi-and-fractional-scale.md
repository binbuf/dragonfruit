# T184 — T-21.1b Chrome HiDPI and fractional scale

| | |
|---|---|
| **Track** | T-21 — Presentation foundation |
| **Release** | v0.1.1 |
| **Depends on** | T183 |
| **Blocks** | T185, T186, T191 |
| **Hardware** | no (nested scale hook is enough; native 1.5x/2x in T191) |

## Goal

Render the shell's chrome at the output's physical resolution and commit it
with the correct Wayland buffer scale/viewport, so menu-bar and Dock text,
icons, hairlines, and glass rims are sharp at 1x, 1.5x, and 2x instead of being
upscaled by the compositor. Logical layout, input coordinates, and the private
layer protocol stay unchanged.

## Context (read first)

- `compositor/src/render.rs` — `update_chrome_preferred_scale()` already
  advertises the output's fractional scale to chrome surfaces via
  `wp_fractional_scale_v1`; `post_repaint()` calls it on every presented frame.
- `compositor/src/state.rs` — the compositor advertises `fractional-scale` and
  `viewporter` (`delegate_fractional_scale!`, `delegate_viewporter!`).
- `shell/src/shellprotocol.cpp` — surface creation and `commitTo()`; there is
  currently no `wp_fractional_scale_v1`, `wp_viewporter`, `set_buffer_scale`, or
  `wp_viewport` handling.
- `shell/src/shellcontroller.cpp` — `renderDock()` and `render()` size the
  offscreen window and commit a logical-resolution image; `onConfigured()` /
  `onDockConfigured()` carry the logical surface size.
- `compositor/src/shell/layer.rs` — layer geometry is logical; panel rects and
  input regions are logical surface coordinates.
- `docs/rendering.md` — R2.2 (HiDPI chrome).
- `docs/design/architecture-audit-native-rendering.md` — §9.5 (shell HiDPI).
- `docs/design/adr/0149-per-output-chrome-reserved-zones.md`,
  `docs/design/adr/0153-per-output-chrome-sizing-and-nested-scale.md`.
- `DRAGONFRUIT_NESTED_SCALE` (`compositor/src/backend/mod.rs`) is the nested
  scale test hook.

## Scope

- [ ] Bind `wp_fractional_scale_manager_v1` / `wp_fractional_scale_v1` from the
  registry and track `preferred_scale` per chrome surface.
- [ ] Bind `wp_viewporter` and create one `wp_viewport` per chrome surface.
  For fractional scales, commit a physical-size buffer and set the viewport
  source/destination so the compositor maps it onto the logical surface size.
  For integer scales, use `wl_surface.set_buffer_scale()` where exact.
- [ ] Add a pure `ChromeScale` helper (C++ or QML-free) that maps:
  - logical surface size → physical buffer size (`ceil(logical * scale)`),
  - logical pointer coordinates → physical buffer coordinates (and back),
  - buffer scale / viewport source / viewport destination for 1x, 1.5x, 2x.
  Unit-test it without Wayland or QML.
- [ ] Render the QML scene at physical resolution while keeping QML layout in
  logical units. Use `QQuickRenderTarget::setDevicePixelRatio()` or an
  equivalent root-item scale; do **not** merely enlarge the window and leave
  pointer injection or QML anchors in physical coordinates.
- [ ] Apply the same treatment to the menu bar, Dock, Dock popovers, menu
  popovers, Control Center, notifications, OSD, overview/switcher, drawer, and
  lock/portal overlays. A shared helper is preferred over per-surface copies.
- [ ] Recompute sizes on `preferred_scale` changes, output scale changes,
  configure events, and hotplug; preserve the logical panel rect and input
  region sent to the compositor.
- [ ] Keep the current 1x behavior bit-identical where possible.

## Out of scope

- Removing `grabWindow()` / SHM copies (→ T185).
- GPU-backed transport (→ T186).
- Per-output refresh scheduling (→ T187, T188).
- Compositor material or blur changes (→ T189, T190).

## Design notes

- The compositor's `chrome_render_elements()` already renders layer surfaces
  through Smithay's surface tree, which honors the surface viewport. The shell
  must set the viewport; do not add a compositor-only scale hack.
- `wl_surface.set_buffer_scale()` accepts integers only. For 1.5x, use
  `wp_viewport` with a physical-size buffer; for 2x, either integer buffer
  scale or viewport is acceptable, but pick one path and test both.
- The **logical** surface size is the contract with the compositor: layer
  configure, reserved zones, `set_panel_rect`, input regions, and pointer
  events stay logical. Only the buffer and viewport are physical.
- Do not change the private protocol. `df_output.scale` already exists for
  shell policy; `wp_fractional_scale_v1` is the per-surface preferred scale.
- If a surface is unmapped, its viewport/buffer scale must not keep stale
  physical geometry; reset on configure.
- Nested testing uses `DRAGONFRUIT_NESTED_SCALE=1.5` (and `2.0`); the nested
  backend is the fast correctness rail, not native proof.

## Acceptance criteria

- [ ] At 1x, 1.5x, and 2x, the Dock and menu bar commit a buffer whose size is
  the physical size of the logical surface, with the correct buffer scale or
  viewport; `chrome stats` reports `logical_size`, `buffer_size`, and
  `buffer_scale` consistently.
- [ ] Text, icons, hairlines, and the Dock/menu-bar rim are rendered at native
  resolution (no compositor upscale) at 1.5x and 2x, confirmed by a before/
  after crop from the nested capture.
- [ ] Layout, panel rects, reserved zones, pointer hit-testing, drag targets,
  and keyboard focus are unchanged at 1x/1.5x/2x.
- [ ] Scale changes at runtime (Displays pane or `df_output.set_scale`) and
  output hotplug reconfigure chrome without a stale-size frame.
- [ ] `ChromeScale` unit tests cover 1x/1.5x/2x rounding and round-trip pointer
  mapping.
