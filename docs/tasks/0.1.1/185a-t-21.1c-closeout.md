## Design notes

- Do not redesign the T185 transport. Fix only a regression the gates expose.
- Use the same nested baseline harness as T185; the after-report is the
  acceptance evidence, so keep its command and scenario set stable.
- A passing `make e2e` is required even though the transport work already
  landed; the global verify is the objective trigger.
- The visual check must be a real nested run, not just the committed still.
- If a converted surface cannot render or accept input through the producer on
  the software backend, keep that surface on the old path and name it with a
  measured reason; do not silently double-render it.
- Keep the private layer protocol and surface roles unchanged.

  from `shell/src/CMakeLists.txt`, and removed its two `tst_dockcore` tests.

### Transport after-report

The committed `docs/captures/t21-chrome-transport-after.txt` was regenerated
on the final tree with:

```text
OUT=docs/captures/t21-chrome-transport-after.txt \
T21_REPORT_TITLE='T-21.1c chrome transport after' \
T21_TRANSPORT_LABEL='QQuickRenderControl -> ping-pong QImage -> pooled wl_shm (3 buffers/surface) -> wl_surface.commit + wl_surface.frame' \
bash scripts/t21-chrome-baseline.sh
```

The final-tree run on the host session was **host-throttled** (the nested
window was not presented at 60 Hz): its Dock sweep is 4 commits / 1,297,760
copy bytes / 0 callbacks / 4 `fallback_renders`, and its idle interval is
shell-zero with 6 compositor frames and 12 client wakeups from the host. The
report states that caveat and keeps the accepted 18:57 run as the target
comparison. A corroborating final-tree run on a KWin virtual host (nested
output 1920x1200, `WAYLAND_DISPLAY=kwin-t21`,
`XDG_RUNTIME_DIR=/tmp/opencode/kwin2`, `SOCKET=dragonfruit-t21-kwin`) produced:

| metric | T183 baseline | accepted 18:57 | final tree (KWin virtual) |
|---|---:|---:|---:|
| `grab_renders` | 280 | **0** | **0** |
| commits | 291 | 136 | 136 |
| `shm_allocs` | 291 | **4** | **3** |
| `shm_bytes` | 268,929,360 | 1,198,560 | 983,520 |
| `copy_bytes` | — | 121,280,880 | 123,177,360 |
| `frame_callbacks` | 0 | 105 | 78 |
| `fallback_renders` | — | 0 | 0 |

Dock per-surface on the KWin run: 128 commits, one new shm allocation, and
122,880,000 copy bytes = exactly **960,000 B (1920x125x4) per committed

`commit_us` p50/p95/p99 = 1,086 / 1,513 / 1,626 µs; frame-callback p50/p95/p99
= 27,086 / 31,092 / 31,727 µs. The idle snapshot had zero shell scene frames,
commits, and grab renders.

### Lock surface and restart

Lock smoke test (nested, same run): the system menu's Lock Screen row was used
because the synthetic `Cmd+Ctrl+Q` chord did not set the Meta modifier on this
host. `query lock` went from `locked=0 surfaces=0 lock-focus=0` to
`locked=1 surfaces=1 lock-focus=1`; three `KEY_A` presses left it focused and
the lock still shows three password dots. `docs/captures/t21-chrome-lock.png`
is the captured lock surface. This proves the lock surface maps and accepts
keyboard input through the converted producer/pacing path; PAM/authentication
remains out of scope.

Shell restart (`scripts/t21-closeout.sh` real-host run): `SIGKILL` the shell,
the compositor reissued the launch token, then the shell was relaunched with
its captured argv/environment and the new token:

```text
old_pid=56079
token_reissued=True
restarted shell pid=56726
chrome_path=True
```

The restarted shell authenticated on the same private layer protocol and
logged `Dock scene-graph commit path active`; windows/outputs survived. No
private layer protocol or surface role changed.
