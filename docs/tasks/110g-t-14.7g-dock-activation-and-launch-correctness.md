## Goal

Every Dock click does exactly what the macOS-like click tree promises, and a
launch never silently no-ops. Today clicking a pinned app may not open a window
and clicking a running app may not switch to it; this unit audits the whole
path, fixes the causes, and makes a failure visible instead of silent.

## Current behavior / hypotheses to confirm (T101 era)

- **Launch environment.** The shell forces `QT_QPA_PLATFORM=offscreen` for
  itself and `appLaunchEnvironment` switches it to `wayland` for children, but
  children still need the session's `WAYLAND_DISPLAY`/`XDG_RUNTIME_DIR` (or
  `DISPLAY`). If the shell was launched with `--socket-name` and did not
  export `WAYLAND_DISPLAY`, a launched client has no display and never maps —
  which presents as "clicking does nothing".
- **Activation has no failure signal.** `activate_app` is fire-and-forget; if
  the app's `app_id` in the projection does not match the window's app id, or
  the window is gone, the Dock does nothing and the user sees a dead click.
- **Tap/drag arbitration.** A click that drifts past the DragHandler threshold
  becomes a rearrangement instead of an activation; a click while the pointer
  arrived through the transparent band, or while a bounce runs, should still
  activate.
- **Missing identity.** After T-14.7 an absent app-index leaves pinned
  entries unresolved (`missing`); clicking must say so (notice), not no-op.

## Design notes

- The click tree is the product contract from `04-shell.md`; a case that
  cannot work must produce a notice, not silence.
- Keep the compositor as the sole activation authority; the shell never
  re-derives "which window".
- The launch environment must be identical for every launch path (Dock,
  menu bar `openApp`, Files reveal) — one helper, one test.

## Hand-off

**State: done.** Root causes fixed and made observable.

Root causes found (all reproduced in the nested demo with synthetic input and
per-hop logs):

1. **Launch environment.** `appLaunchEnvironment` only scrubbed
   `QT_QPA_PLATFORM=offscreen`→`wayland`; it never exported the compositor
   socket. A shell started with `--socket-name` and no `$WAYLAND_DISPLAY`
   launched a client with no display. Fixed: the helper now takes the socket
   the shell connected on and inserts `WAYLAND_DISPLAY`; `XDG_RUNTIME_DIR` is
   inherited. Every launch path (Dock, menu `openApp`, Files reveal) uses the
   one helper.
2. **Activation had no failure signal.** `df_toplevel_manager.activate_app`
   was fire-and-forget. Added additive v8 event
   `activation_result(app_id, found)`; the compositor sends it on the
   requesting manager. The shell remembers the desktop id per app id and on
   `found=false` launches the entry or raises a notice.
3. **Missing identity was silent.** A `missing` pinned entry now raises a
   real notice (`raiseDockNotice`) and keeps its not-found mark.
4. **Tap/drag arbitration** now shares one slop (`dockEntry.dragSlop`, 8 px)
   between the left `TapHandler` and the `DragHandler`.

Activation-result mechanism chosen (see **ADR 0101**): a minimal additive
event, keyed by `app_id`, sent only to the requesting manager; the compositor
stays the sole activation authority. No state-machine rewrite.

Live/synthetic limitation (recorded, not hidden): the shell's synthetic pointer
path cannot land a tap on a Dock entry that also carries a `DragHandler`
(app/temporary entries); Trash/minimized/stack entries tap fine. The QML unit
tests (QtTest event synthesis) prove the stationary-click and slop-drag
contract, and the live capture drives the same controller path through the
`DF_DOCK_ACTIVATION_FIXTURE` capture seam (like T-14.7e/f). Follow-up: make the
live synthetic tap path land, then re-capture without the fixture.

What T-14.7h (folder/stack click semantics) must know:

- `activateEntry` in `Dock.qml` handles `kind === "stack"` by opening the
  stack popover before the running/chooser logic; folder semantics belong
  there or in a new kind, not in `onDockEntryActivated`.
- The controller's `activateAppOrFallback(appId, desktopId)` is the one
  activation entry point; keep using it so the `activation_result` fallback
  stays wired.
- `appLaunchEnvironment(base, waylandDisplay)` is the only launch-env helper;
  `ShellController::m_waylandDisplay` holds the socket.
